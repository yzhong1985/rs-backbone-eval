范围：`docs/architecture/RTX5090夜间算力接入与T10B2安排_2026-11-04.md`
的决策、启动条件、夜间排期与回传验收；结合当前 lane、T10 worker、审计脚本和

总体判断：LAN 传输、原始压缩包不作为训练依赖、三个种子同 host/GPU、只搬缺失 cell

## 1. P2：文档遗漏 lane 所需的 WSL nvidia-smi PATH 配置

位置：方案第 20 行、§3.3 和 §10 的启动步骤。

文档明确 `/usr/lib/wsl/lib/nvidia-smi` 不在 PATH；示例 `.env` 未补 PATH，
`scripts/rerun_baselines.sh:125` 又直接调用 `nvidia-smi`。因此按文档记录的环境执行
T10B2，若该路径条件仍成立，会在 dispatch 前报 `no GPU visible`，torch 的 CUDA 验证成功
也无法绕过这一步。

审查后段执行环境切换到了 YZ-WORKPC，本机只读复查已经可以通过 `command -v nvidia-smi`
找到 `/usr/lib/wsl/lib/nvidia-smi`，所以**不认定当前节点仍有此启动阻断**。问题是文档未记录
如何满足此依赖，照文档复现或换一个启动环境仍可能失败。

已用完整 T10B2 入口和临时 stub 复现（未启动真实 worker）：

| 条件 | 退出码 | dispatch 次数 |
|---|---:|---:|
| nvidia-smi 在模拟 WSL 目录、该目录不在 PATH | 1 | 0 |
| 将该目录加入 PATH，返回 GPU 空闲 | 0 | 2 |

建议：在启动环境持久加入 `/usr/lib/wsl/lib`，并让 detached 子进程继承；或为脚本增加
明确的 WSL 可执行文件回退。正式起跑前验证 lane 的 GPU 空闲检查，不使用 CPU-only 标志
绕过 GPU 检查。

复现日志：`/tmp/rs-5090-plan-review-lbcyspt_/`。

## 2. P2：audit_runs.py 不承担方案声称的完整回传验收

位置：方案 §6.3 第 153 行。

该步骤写为运行 `scripts/audit_runs.py` 后确认 git_commit、host/GPU、manifest 和预算。
当前脚本检查修复提交祖先关系，以及 full_finetune 的训练参数语义；读取记录时未取出
host/GPU、manifest hash、optimizer_steps，因而不会验证这些条件。审计返回成功不能证明
同一 cell 的种子确实同机器、同 manifest、同预算。

正式预算另由 `matrix.formal_candidates` 检查，这一点已有保护；但不能把该保护和
修复祖先审计合称为已经检查完整 cell。

建议：把验收拆成修复祖先审计与 cell 一致性检查，列出每条 run 的实际设备、manifest
hash、checkpoint hash、preprocessing_id、micro/accum、optimizer_steps，并核对预声明的
种子集合。回传前还应检查目标 run_id 不存在，避免 rsync 合并或覆盖另一个尝试。
这不要求修改已有 run.json。

## 3. P2：一晚两 seed 缺少完整耗时依据和最晚启动条件

位置：方案 §6.1 第 129–131 行、§7、§10。

已只读核对 4090 的 v7 三条完成记录：

| seed | train_seconds | eval_seconds | 两阶段合计 |
|---|---:|---:|---:|
| 17 | 11398.9 | 825.2 | 3.396 h |
| 42 | 11398.6 | 811.4 | 3.392 h |
| 73 | 11370.5 | 814.0 | 3.385 h |

来源：`yzhong@192.168.1.89:/geodata/rs-eval/runs/lim_mit_huge-T10-rotated_frozen-train-{17,42,73}-v7/run.json`。
旧 v7 指标不用于新口径比较，此处仅作为耗时规划的历史参照。

文档引用的约 3.1 h 基本是训练阶段。`t10.py` 在 test 评估前读取 wall，账本的
wall_time_seconds 也不含这段最终评估；按它规划占卡结束时间会少算评估。
5090 的 2–2.5 h 仍是估计，已有 matmul 和待测 DataLoader 吞吐均不能测出完整检测训练速度。
lane 的 STOP_ON_FAIL 只处理失败，不会根据白天用机时间阻止 seed 42 启动。

建议：先做独立诊断 run，测量稳定的 optimizer step 耗时，并预留评估、checkpoint、
回传与中断恢复时间；明确用机截止时间和第二个 seed 的最晚启动条件，窗口不足则留到
下一晚。T10 checkpoint 在 epoch 边界保存，不能假设临时停机只丢最后几个 step；以
15389 train tiles 和既有 4.39 tiles/s 粗算，一整个 epoch 接近一小时。

§7 的 12 epoch / 550 GB 估算也应标为循环上界：正式 25000 optimizer steps、有效 batch 2
约消费 50000 tiles，相当于 3.25 个 epoch。按原文每 tile 约 3 MB 的逻辑估计约为 150 GB；
真实物理 I/O 仍应实测，不能由窗口字节数直接推出。

## 各项决策建议

- **D1：认可。** 优先 LAN，只同步训练所需 payload 与溯源文件。
- **D2：可作为临时部署手段，有条件认可。** 同架构、同仓库路径并不足以独立保证 venv
  可运行。已只读确认源端两个 venv 都依赖 `/usr/bin/python3.12`（pyvenv.cfg 为 3.12.3）；
  目标需提供匹配的解释器和系统库。后段在 YZ-WORKPC 本地确认了 Python 3.12 存在，
  LIM venv 的 pyvenv.cfg 同为 3.12.3。仍应在复制后的 LIM 环境执行实际 worker 入口，做 CUDA
  前向、反向、optimizer step，以及 torchvision 的 NMS / RoIAlign 检查。现有方案仅安排
  样本解码，matmul 不能覆盖检测算子。此处是待补验收，不断言目标环境已经损坏。
- **D3/D4：认可 E 盘暂存与排除 downloads。** derived 标注、固定 manifest、provenance
  与权重仍是依赖，不能把“只传 images”理解为完整部署清单。先实测训练是否被 I/O 限制，
  再决定搬 images；避免仅因未达到任意的 30 samples/s 阈值就搬盘。
- **D5：认可。** seed 73 继续放 5090；回退 4090 时按风险表所述迁移整个 cell，使用新
  run_id，保留原尝试。应将此限制同步写到 §8 的回退步骤，避免被理解为只迁移失败的 seed。
- **§7：先保留当前布局。** 若确认 I/O 是瓶颈且宿主盘空间核对通过，短期只搬 images；
  迁移整个 WSL 发行版另排维护窗口。
