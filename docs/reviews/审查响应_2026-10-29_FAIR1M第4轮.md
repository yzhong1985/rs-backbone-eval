## 1. 必修：推理解码与训练编码不一致

### 复现

`detectors()` 里 `decode(boxes[keep], deltas[keep, class_id])` 把 `cx, cy, w, h, θ` 的
proposal 当成 `x1, y1, x2, y2`。同一组目标：按训练方式解码还原出 `(305, 398, 64, 22, 0.35)`；
按旧推理解码得到 `(161, 231, -243, -227, 0.35)`，宽高为负。后果正如你所说：所有预测框都是
错的，test mAP 会接近 0，B1D 的 validation 选模也失效。

### 修复

`decode(hull(boxes[keep]), deltas[keep, class_id])`（`detection/detector.py`）。同时补两个用例：

- `test_encode_decode_recovers_the_ground_truth_from_a_proposal`：对同一 proposal 做
  `encode` 再 `decode`，断言还原 GT；并断言"用 cx,cy,w,h 直接解码"会得到负宽度，把这个失败
  形态固定下来；
- `test_inference_returns_positive_boxes_inside_the_image`：跑真实推理路径，断言框的中心在
  图像内、几何尺寸为正。

另外补了一个不在你清单里、但同源的缺陷：`decode` 只夹取框中心，宽框仍可能整块越界。现在
worker 在把 tile 预测转成 `Detection` 时用 `clip_polygon` 与 tile 求交，完全落在外面的直接丢
（`detection/nms.py`，附单测）。这样进入整图合并与 AP 的框都在画面内。

## 2. 建议：val 派生标注里的图像尺寸是旧的

确认：`derived/fair1m/obb/*.json` 在替换 val 影像之前生成，重建 manifest 时因为文件已存在
而没有重写，于是 1,274 个 val 场景的 `width/height` 还是旧影像的。这不只是文档不一致：worker
用标注里的尺寸推算真实像素矩形，并和 manifest 的 `valid_fraction` 交叉校验，**这些 tile 在
评测时会直接抛错**，test 根本跑不完。

处理：

- builder 现在会读缓存标注的尺寸，与影像实际尺寸不一致时**重写**该文件并把次数记进
  `BuildStats.stale_annotations`（新增用例覆盖：造一个尺寸被改坏的标注，重建后应被修复且计数为 1）；
- 用 `RS_EVAL_FAIR1M_REBUILD=1` 全量重建：`489.json` 从 `1500x1500` 变为 `600x800`；
- 重建 manifest（1024 / 512 / holdout），并**在 worker 侧实测**：从 validation 与 test 各取 4 个
  tile 过 `Fair1mTiles`，尺寸交叉校验通过（修复前这里会抛 `ValueError`）。

## 4. Clay 的资源阻断（同步给上级）

3080 实测：Clay 1024 单张 forward ≈ 5.2 s，几乎全在 encoder（全注意力，16,384 token），
UPerNet 头只有 0.06 s；512 为 0.38 s。按 25k step × 8 = 20 万 tile 折算，1024 在 3080 上约
290 h/种子、4090 上估计约 110 h。显存够（6.4 GB / 20 GB），是算力不够。因此 Clay 的 iSAID
B2U 记为资源阻断、暂不排期；若要纳入，只能以预先声明的 512 独立 cell 出现（约 23 h/种子）。
