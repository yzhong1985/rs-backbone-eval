## 1. 切块公式（必须修的 bug）

旧实现两个错误叠加：

1. 任一边 `< crop` 的图 **整张跳过**（train 418/1411、val 140/458）；
2. 只按整步长向下取整，**最后一条边缘带没有块**。

后果：像素覆盖只有约 **80%**。训练端会丢掉三成图（小图构图与类别分布不同，会引入偏差），**评测端更致命**——官方 mIoU 在整张图上计算，必须 100% 覆盖。

**修正后**（`tiles_padded()`）：

- `ceil((dim - crop) / stride) + 1`，边缘块 pad；
- 小于裁块的图 → 整图 pad 成 1 块；
- 像素覆盖 **100%**。

**重算结果**（与评审实测一致）：

| 配置 | 训练（旧 → 新） | 验证（旧 → 新） |
|---|---|---|
| 1024/512 | 20,022 → **29,457** | 6,960 → **10,132** |
| 1024/1024 | 5,841 → **11,828** | 2,047 → **4,055** |
| 512/256 | 109,636 → 131,299 | 37,724 → 44,936 |
| 512/512 | 29,472 → 41,672 | 10,149 → 14,222 |

覆盖遍数随之修正：20 万样本 ÷ 不重叠 11,828 块 ≈ **17 遍**（原写"34 遍"）。

## 2. 校验和

旧代码循环结束后 `source` 指向 val 的 json，却写进了 `{"train": ...}`。

**修正**：对 **2 个标注 json + 2 个掩码 zip + 4 个 DOTA 图像 zip = 8 个文件**逐个计算 sha256，写入 `p0a_report.json` 的 `sha256` 段，可直接满足 §4.5 的溯源要求。

## 3. 一致率的口径

旧实现 `votes[name][colour] += 1` 统计的是**实例里出现某颜色的次数**，不是像素；"3,477 万像素"只是总量，一致率本身没有加权。

**修正**：改为 `votes[name][colour] += 该颜色像素数`，并输出每类的**第二颜色及其占比**。

结果（像素加权）：

- 16 色、**无冲突**（结论不变）；
- **Ground_Track_Field 0.611**，第二颜色 `#007fbf`（Soccer_ball_field）占 **36.7%** —— 印证评审的判断：内场草地在语义图里被涂成足球场，属**实例重叠时的覆盖顺序**，不是调色板错误；
- Harbor 0.966、Bridge 0.994、plane 1.000（旧的 72%、82% 确系 bbox 中心取色造成的假象）。
