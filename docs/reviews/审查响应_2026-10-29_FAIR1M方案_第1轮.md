## 1. 先澄清需求：比较不同主干接同一个检测器

用户已明确，上级希望看的是 **不同 backbone + 同一 Faster R-CNN 检测头** 的比较。因此，本轮以 **Rotated Faster R-CNN** 为统一检测器，保留 FAIR1M 的旋转框任务定义。Oriented R-CNN 不再作为未经确认的默认替代方案。

“LIM + ResNet-50”是此前容易误解的简写，实际指两组独立实验，并不拼接或融合两个主干：

| 实验 | 主干 | 下游检测结构 | 作用 |
| --- | --- | --- | --- |
| LIM 检测实验 | LIM / MiT-Huge | 统一 FPN + RPN + RoI 检测头 | 业务要求中的主干能力比较 |
| R50 复现锚点 | ResNet-50 | 同类 Faster R-CNN 检测结构 | 先验证实现和训练管线能否复现参考结果 |

**ResNet-50 不能替代完整的多主干评测目标。** 原有比较对象为 LIM、AnySat、Clay、Prithvi、OlmoEarth Tiny/Base；R50 作为校准参照。MaRS 和 Galileo 的新增可行性见[独立调研文档](../models/MaRS与Galileo接入评测可行性_2026-10-29.md)。

### 1.1 “同一个 Faster R-CNN head”具体控制什么

首版锁定同一个逻辑实现、head 配置和版本，包括：

- FPN 输出 256 通道，固定输出层数及尺度定义；
- RPN 的 anchor、匹配、采样、proposal、损失和 NMS；
- RoI 特征提取及两个全连接层，37 类前景分类和旋转框回归；
- 框编码、角度范围、损失、合并、阈值和评价器。

各主干允许其必要的输入/特征适配，但必须报告适配器训练状态、参数量和输出步长。不同原始通道数导致 FPN 入口卷积形状不同，应如实记录；不能把“同一检测结构”写成所有模型的每个权重张量都相同。

普通 Faster R-CNN 输出水平框。FAIR1M 正式路线使用其旋转框版本；若业务最终要求水平框，需另建 HBB 任务，不能把 HBB 与 OBB 成绩直接合表。

## 3. 检测后端：架构决定必须先于算子验证

### 3.1 已核对的环境快照

通过各 worker 的已安装 `torch-*.dist-info/METADATA` 读取，而不是仅看依赖声明：

| worker | 已安装 torch |
| --- | --- |
| AnySat / Prithvi | 2.14.1 |
| OlmoEarth | 2.9.1 |
| Clay | 2.4.0 |
| LIM | 本次未发现独立环境中的已安装 torch metadata；`pyproject.toml` 声明 `torch>=2.4`，不能据此认定已安装版本 |

原代码的 MMRotate 0.3.4 依赖 MMCV-full 1.x / MMDet 2.x，不能当成能与这些环境直接共享的普通 Python 包。MMCV 2.x 或 Detectron2 仍涉及原生扩展和 torch ABI；“各环境编译一次”是需要验收的工程工作，不是已解决的兼容性事实。

也不采用“4090 必须 CUDA 11.8 才能运行”的绝对表述：11.8 支持原生 Ada 编译，某些较早的 cubin/PTX 可兼容；具体组合仍需验证，见 [NVIDIA 官方说明](https://docs.nvidia.com/cuda/ada-compatibility-guide/)。

### 3.2 建议采用的双层架构

**参考验证层：** 单独的冻结依赖环境运行公开的 Rotated Faster R-CNN R50 实现及 checkpoint。它只用于复现与数值对齐，不要求装入全部现有 worker，也不把其分数直接混入冻结主干主表。

**正式比较层：** 共享同一份 torch 检测逻辑，移出对 MMRotate/MMDet registry、runner 和 dataset 的依赖；首选配套 torchvision.ops 预编译包承担水平框训练算子，CPU Shapely 承担旋转后处理与多边形评测；不要求各 worker 编译 MMCV。控制层不导入 torch，原生扩展不放进根环境。模块路径和包边界属于待实施设计，不声称已有共享检测包。

参考配置使用水平 proposal、普通 RoIAlign，再做旋转框回归，不能误写成必须采用 Oriented RPN / RoIAlignRotated。普通 RoIAlign、水平 NMS，以及后处理需要的旋转 NMS/IoU 等依赖按实际实现列清楚；所有模式核对 `aligned`、坐标顺序、采样、角度和精度约定。[参考配置](https://github.com/open-mmlab/mmrotate/blob/main/configs/rotated_faster_rcnn/rotated_faster_rcnn_r50_fpn_1x_dota_le90.py)

### 3.3 G0 后端架构准入

全主干比较前必须交付：

1. 共享 head 逻辑的 source hash、参考实现/配置 commit、算子接口清单和依赖矩阵。
2. 每个拟纳入 worker 的 torch/torchvision 配套安装、算子加载与可重复环境；不复用其他 torch 版本的 `.so`，也不把安装 torch 等同于 torchvision 算子可用。
3. 同一输入/权重的 head 输出、损失、框解码、RoI 特征梯度和 NMS 等价性验证；规定浮点容差和同分排序规则。
4. 各主干的单 batch head 训练与必要输入适配器的反传验证。

如果 G0 不通过，阻断相应 worker 的正式比较，报告“接入阻断”；不能悄悄改成另一个检测器或记零分。R50/LIM 的工程验证可先进行，但不会被宣称为“全部主干比较已完成”。

完全冻结编码器与全部入口适配器时，可以另外评估离线特征交换，绕开跨环境反向图；缓存容量、增强和预处理必须单独设计。有可训练输入适配器或全量微调时，单纯导出特征不能保留反向路径，不能用这条路径假装实现同一协议。

## 4. G1：管线正确性与精度锚点

### 4.1 先验证 checkpoint 推理

下载公开 R50 + Rotated Faster R-CNN checkpoint，锁定相匹配的数据、标注和评测脚本，对齐官方实现与拟使用的共享 head。覆盖图像读取、四点框转换、切片、原图合并、类别映射与评测；不能仅测试合成框或单张可视化。

相同 checkpoint 的差异应追到具体数值/后处理原因，不用宽松的 1–2 AP 容差掩盖实现错误。

### 4.2 再做标准训练复现

优先采用数据和参考成绩都能取得的 DOTA-v1.0，R50 按对应官方 1x 配置训练；按参考设置保留其冻结层和 BN 行为，不能自行改成完全解冻仍叫同一复现。另需核对 DOTA 检测标注，已有影像不代表标注已具备。

公开 MMRotate 的同类参考表给出 R50、1024 切片、200 重叠、le90、1x 的 DOTA-v1.0 mAP **73.40**。这是所列参考协议的成绩，**不是本地 val 目标，也不是 FAIR1M 的目标值**。[参考表与模型](https://github.com/open-mmlab/mmrotate/blob/main/configs/rotated_faster_rcnn/README.md)

若获得完全匹配的评测集/协议，可预设复现差距 1–2 个 AP 百分点为训练验收参考。测试服务器不可用时，改为锁定同一可评测 split 上的参考 checkpoint/参考实现成绩，并清楚标注内部校准；不能拿别的 split 硬对齐 73.40。

R50 的标准训练锚点与后续冻结主干比较不是一条轨道。若把 R50 加入冻结主干主表，必须另跑冻结 R50 + 统一头的实验。

## 5. 37 类、五大类与尺寸分层

37 类 mAP 保留为细粒度任务指标，五大类 mAP 与目标尺寸分层召回同时必报。是否触底、哪些类别触底由实际预测、GT 数和种子结果判断，不能根据 patch 大小提前定论。

五大类指标从同一份 37 类预测映射类别，在预先锁定的合并/NMS 规则下重新计算 AP；不能把 37 个 AP 相加/取均值冒充五大类 AP。类别不可知检测是所有目标归一类的另一项指标，不叫五大类 mAP。

如果另训练五分类检测头，属于监督任务已改变的附加实验，使用不同配置/结果 panel，不替换 37 类主任务。

目标尺寸以原图像素中的 GT 多边形面积定义，训练前固定分档、IoU 阈值和 max detections。报告每档 GT 支持数、召回和计算规则；不因某个主干结果不好再调整阈值。

## 6. 默认数据划分与 iSAID 关系

默认取得经核实的 FAIR1M-2.0 官方 train 后，**先按原图/场景分组划 train/dev，再切 tile**，命名 `FAIR1M2-train-holdout`。建议 dev 约 12%、固定种子 17，P0 检查各类覆盖和按图/块/实例比例后一次性锁定，不能按各模型表现反复挑划分。

dev 用于锁定协议允许的选模/调参，报告是内部开发集成绩；若需要独立最终测试，应另锁未用于调参的 holdout 或适当的官方 split。官方测试标签/服务器不能作为保证可用的默认条件。

已有检测需求已经明确。建议在 iSAID 首批 B2U 结果后释放 GPU 预算进入检测 P1；此前可以做下载清单、数据审计和 CPU 开发。iSAID 可以帮助评估空间细节和成本，但“分割触底 ⇒ 检测必然更低”不能作为自动取消检测的规则。

## 7. 预算准入修复必须提前

**第一轮快照**：当时 `matrix.py` 含 `T9: 50`，因此“所有 T9 短跑只能靠 SMOKE 字样拦截”已不符合最新代码。但只读探针仍发现下列行为：

| 输入 | 当前 `is_reduced_run` | 解释 |
| --- | --- | --- |
| T9，1 epoch，无 notes 标记 | True | 会识别短跑 |
| T9，0 epoch、0 step，无 notes 标记 | False | 完成量缺失没有被预算检查拦截 |
| T9，50 epoch、1 step | False | 不核对 step 一致性；这是函数探针，不是声称存在这样的真实 run |
| T10，1 epoch，无 notes 标记 | False | 未定义预算的任务默认不会被该函数识别为短跑 |

**第二轮纠正**：第一轮漏查 `workers/lim/src/lim_worker/t9.py` 自持的 `OFFICIAL_EPOCHS=50`，它也会写 REDUCED-BUDGET。即使控制层改成 step 准入，旧 notes 仍可能先行排除完整 step 运行。该共享判断已在 `94ac560` 提交，`9b9826c` 记录 quarantine 与 v2 重跑；此前“尚未提交”的表述已过时。基于已提交代码复现后，`11bafd4` 进一步以权威 25k step 预算修复自报短预算及零/未知完成量准入；验收见第二轮响应 §3/§7。历史错误 notes 不会自动改写。

拟修复规则：预算由 task/protocol 声明，区分 `epoch` / `optimizer_step`；epoch 制核对 epoch 完成量及合理的 step 证据，step 制核对真实 optimizer steps。预算未注册、完成量未知/零、协议不一致的结果不进入正式表。不要仅给 `OFFICIAL_EPOCHS` 加 T10 就认为覆盖了 step 制 smoke。

此修复要在正式结果准入前完成，回归同时覆盖 matrix、报告、Portal 和 canonical seed 选择。现有 tag 可作审计信息，正式字段/接口修改需按 schema 评审实现；**本次文档没有修改运行或聚合代码**。

检测有效 batch 初步建议 2，属于独立检测配方，参考经典检测配置且适应单卡资源；它与 iSAID 已定的有效 batch 8 是两个任务协议。梯度累积 1×2 与真实 micro batch 2 不一定数值等价，R50 复现锚点应遵守自己的原始 batch/调度设置，不能只看乘积相同。
