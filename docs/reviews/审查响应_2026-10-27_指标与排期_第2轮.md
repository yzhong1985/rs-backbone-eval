## P1：波长消融会混入基线

### 问题成立的原因

`T1S_WL` 的四种条件与正式基线**共用** `task/model/protocol/seed`，只有 run id 后缀不同：

- `matrix.canonical_runs()` 在**同一组内按 seed 去重**，多个同 seed 运行时"最近更新的官方预算运行"胜出；
- `variant_key()` 里没有波长这一维，因此四组条件与基线属于同一 group。

结果：`wl-base` 会顶替 seed 17 的基线，`wl-phys/swap/same` 再依次顶替——报告与 Portal 上的 T1S 单元会变成某一次消融。审查复现的正是这条路径。

### 修复

**物理隔离，而不是继续加分组条件。** 原因是：即便把波长加进 `variant_key`，四组条件仍会作为"同 cell 的不同 variant"参与 headline 选择（种子数相同，谁胜出取决于遍历顺序），风险没有消除。

| 位置 | 改动 |
|---|---|
| `scripts/rerun_baselines.sh` | `T1S_WL` 注释明确标注 **DIAGNOSTIC, NOT A RESULT**，并写明必须设置 `RS_EVAL_RUNS_ROOT` 指向诊断目录及原因 |
| 3080 `run-t1s-wl.sh` | 导出 `RS_EVAL_RUNS_ROOT=$HOME/rs-eval/runs-diagnostics`，日志打印实际写入目录 |
| 本地 `sync_t1s_wl.sh` | 只 rsync 到 `/geodata/rs-eval/runs-diagnostics`；**不跑 audit、不刷新报告、不进 Portal** |
| 旧的 sync watcher | 已终止（它会写正式账本） |

### 验证

- 正式账本中 `*-wl-*` 记录：**0 条**；`runs-diagnostics` 目录为空（消融尚未开始，正等待 `T1HOLDA` 完成）。
- 因此本轮是**设计层面的隔离 + 已移除污染路径**，尚未经过一次真实运行的端到端验证；消融跑完后会再核对一次"正式账本零 `-wl-` 记录"。

## P2a：T5「去背景 mIoU」语义错误

### 问题成立的原因

`multiclass_metrics` 里写死了"剔除 class 0"。实际情况：

| 任务 | class 0 是什么 | 剔除是否正确 |
|---|---|---|
| T1 / T1S / T2 | 陆地 / 未烧（背景） | ✅ |
| T3 | 无火烧（占比 70%，非目标类） | 🟡 可作背景，但需声明 |
| T4 | 非滑坡（背景，占 98%） | ✅ |
| **T5** | **有效作物类别（Natural Vegetation）** | ❌ 错 |
| **T8** | **忽略类（标签重映射后 0 不参与统计）** | ❌ 无意义 |

### 修复

- **撤销** `multiclass_metrics` 中的 `mean_iou_no_background`：纯指标函数不该知道任务语义；
- `TaskSpec` 新增 `background_class: int | null`，在 `configs/tasks/*.yaml` 里**逐任务声明**：T1/T1S/T2/T3/T4 为 `0`，**T5、T8 不声明**；
- 报告 §2.3.2 改为读取声明：未声明或该背景类未出现时显示「—」，不再静默剔除。

### 验证（重新生成的报告 §2.3.2）

|---|---|---|---|---|

| T5 Prithvi B1 | — | — | 0.4115 | — |
| T5 Clay B2 | — | — | 0.4780 | — |

主指标不受影响：T5/T8 的 headline 仍是完整 mIoU。

## P2b：重算脚本漏掉新增指标

### 问题成立的原因

`scripts/rederive_metrics.py` 用硬编码集合 `CONFUSION_METRICS` 判断"哪些指标可以从混淆矩阵重算"。新增的 `mean_iou_no_background` 不在其中，即使 `--all` 也只会被当作陌生指标原样保留，不会被修正。

### 修复

1. 该指标已随 P2a 撤销；账本中**没有任何**运行记录含此字段（`grep -l` 结果 0 条），无需清理；
2. 新增守护测试 `test_every_emitted_segmentation_metric_is_recompute_aware`：断言 `binary_metrics`/`multiclass_metrics` 发出的每个指标名都出现在 `CONFUSION_METRICS` 中，否则测试失败。这样"新增指标却忘了教重算工具"这一类问题会在 CI 阶段暴露。

## P2c：T3 低分原因被过早定论

### 问题成立的原因

两方面都错：

1. **引用错误**：论文 v2（2412.02732v2）burn intensity 的训练轮数是 **150**，不是 100。我此前把 Landslide4Sense 段落里的"100 epochs"错记到了 T3 上。
2. **结论超前**：T3 的 15.6 与 29.4 之差同时涉及 epoch、损失函数（wCE + Lovasz）、decoder 与调参预算，**在只跑一个 epoch 变量之前不能归因**。

### 修复

- `docs/reports/参考水平_SOTA对照_2026-10-27.md`：改为"论文 v2 为 150 epoch"，并把"已定位到训练预算"改为"候选原因之一，探针验证中"；
- `T3B0EPOCH` lane 注释重写为**假设检验**：跑 100（中间点）与 150（论文 v2）两档，若仍不足则说明损失/配方/decoder 也在起作用；
- 该 lane 仍按"非官方 epoch 计为 smoke"处理，不进正式矩阵。
