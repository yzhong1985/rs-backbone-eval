# 项目与实验审查（2026-10-14）

审查基线：`e5d6fdf`。范围包括设计文档、任务/协议配置、三个 worker 的训练与评价实现、结果汇总和现有报告。未运行 GPU 训练，也未取得外置原始数据、实际运行时的上游 checkout 和历史 run/checkpoint；历史成绩取自仓库报告。因此，当前源码缺陷可以定位，但不能直接认定所有历史运行都使用了同一份有问题的源码。

## 1. 优先处理的实现问题

### P0：冻结主干时，输入适配器的梯度被切断

- 位置：`workers/anysat/src/anysat_worker/t1_adapter.py:169`、`t2.py:158`、`t5.py:126`、`t8.py:135`；Prithvi T8 同样见 `workers/prithvi/src/prithvi_worker/t8.py:153`。
- 调用链为 `adapter(images) -> no_grad 下的 backbone -> head -> loss`。即使适配器参数在 optimizer 中，也无法从 loss 获得梯度。
- 影响：`frozen_adapter` 实际不是报告声称的“训练适配器与头”。缺失波段由初始化后的适配器提供；这些运行不能用于证明学到的光谱适配有效。不能仅靠参数的 `requires_grad=True` 统计“实际被训练”的参数。
- 修复：只冻结 backbone 参数，在需要训练前置 adapter 时保留穿过 backbone 的计算图，同时检查上游 forward 是否自带禁梯度装饰器。纯冻结特征探针才使用 `no_grad` 和缓存。
- 验收：一批数据更新后 adapter/head 参数改变、梯度有限且非零；backbone 参数不变、梯度为空。修复后显存和耗时必须重测。
- 依据：[PyTorch no_grad 文档](https://docs.pytorch.org/docs/2.14/generated/torch.no_grad.html)明确说明，禁梯度上下文中的运算结果不再保留反向梯度关系。

### P0（需核对实际上游版本）：Clay 的 B1 没有显式解冻加载的编码器

- 本项目 `workers/clay/src/clay_worker/t1.py:179` 只在冻结分支设置 `requires_grad=False`，非冻结分支没有设置为 True；T5 的 `ClayT5` 也一样。
- [Clay 官方 SegmentEncoder](https://github.com/Clay-foundation/model/blob/main/claymodel/finetune/segment/factory.py) 的 `load_from_ckpt()` 会冻结加载到的参数。若实际 `CLAY_SRC` 使用该实现，本项目 B1 会继承冻结状态。`train()` 或 `enable_grad()` 都不会自动解冻参数。
- 因此，报告中 Clay “全量微调约 1.4 GB / 4.6 分钟”的成本优势需要先核查训练参数清单与权重更新；低开销本身不能证明 bug，但与这条调用链相符。
- 修复：加载后显式按协议设置所有 backbone 参数；启动时断言 B1 backbone 可训练参数数量，并保存单步更新前后参数差异。检查 T1/T2/T5/T8 共用路径。

### P0：seed 大多只是记录字段，没有驱动随机数生成器

- 在 worker 源码中检索 seed 初始化，只有 Prithvi B0 的 `seed_everything`，见 `t1_baseline.py:341`。AnySat、Clay 和 Prithvi 自定义训练路径没有对应初始化。
- B0 也先在第 266 行构建任务，随后才设 seed，随机初始化的 decoder 已经创建。
- 影响：“seed 17/42/73”不是可复现的随机条件。现有重复运行仍能描述运行间波动，但不能按记录的 seed 重现，也不适合做严格配对分析。
- 修复：在任何模型、adapter、head、DataLoader 构建前统一初始化 Python/NumPy/Torch CPU/CUDA RNG，记录 DataLoader 与确定性设置；保存续训 RNG 状态。

### P0：汇总器混合重复种子与实验版本，且没有正确选择验证集最优配置

- `matrix.py:84` 用 distinct seed 计算 n，但第 85 行将所有 run 纳入均值与标准差；`report.py:247` 同样如此。
- 最小复现重现了现有报告的 Clay T1 B1 行：17=0.7374、42=0.7590、73=0.7658、另一次 42=0.7678 被算成 `0.7575 ± 0.0139，n=3`，实际有 4 个观测。Portal 的逐 seed 字典还会覆盖其中一个 42，与均值的来源不一致。
- `variant_key()` 仅使用 head、预处理名称、LR、encoder 输入大小，遗漏 manifest、权重、预算、裁剪、batch、选模规则及代码/配置版本，容易混合不兼容实验。
- `_rank()` 只看是否存在 `selection` tag 和种子数。该 tag 表示每次训练选择了 validation checkpoint，并不等于该超参是 validation 搜索胜者。最小复现中，两个同种子数候选的 validation 分数为 0.5 和 0.9，调换输入顺序就改变最终入表的 LR。
- 修复：保存明确的 `experiment_config_hash`、`phase=search/final`、`selected_config_id`、`superseded_by` 和 canonical run；按预先指定规则每个最终配置每个 seed 取一条，不按测试成绩去重。相同 seed 的重试不能作为独立种子。统一 report/Portal 的筛选逻辑。

### P0：扰动结果可能被误当成干净测试主成绩

- `contracts.py:141` 的 `primary_metric()` 返回第一个 `is_primary=True` 的指标，不指定 split。
- AnySat 与 Clay T1 先追加扰动指标，最后追加正常 test 指标；各 split 的同名指标都设为 primary。
- 最小复现确认：先插入扰动 IoU=0.3 后，headline 会返回 0.3，忽略后面的正常 test 成绩。开启 D2 后可能污染 D1 排名。
- 修复：显式声明 `headline_metric` 和 `headline_split`；聚合 key 必须包含 split。扰动结果单独展示，并测试加入或重排扰动记录不会改变原始主成绩。

### P1：B0 保存了最佳 checkpoint，但测试评估的是训练结束时的模型

- `t1_baseline.py:316` 创建 `ModelCheckpoint(monitor='val/loss')`；第 353 行直接把 `task` 传给手工测试函数，没有加载 `best_model_path`；第 363 行才把最佳权重登记为 artifact。
- 影响：保存的“最佳模型”和报告分数可能来自不同权重。
- 修复：先恢复被选中的 checkpoint，再调用公共评价器，同时记录选中 epoch、权重哈希与选择指标。若有意使用最后一轮，则明确报告并保存该版本。
- 仓库阶段报告已披露 B0 曾按测试集挑学习率。修复选模之后的新结果应独立版本化；原测试集已经被查看，重跑不会使其重新成为未触碰的测试集。对泛化结论建议增加独立区域 holdout。

### P1：仓库缺少数据代码，无法从干净 checkout 重现

- `tests/conftest.py:9` 与 CLI/worker 导入 `rs_backbone_eval.data.*`，但该目录既不在磁盘，也不在 Git 跟踪列表。
- `git check-ignore -v` 确认 `.gitignore:36` 的 `data/` 规则匹配了 `src/rs_backbone_eval/data/sequence.py`；`datasets/` 规则也需一起检查。
- 实际运行 `PYTHONPATH=src python3 -m pytest --collect-only -q` 在加载 conftest 时失败：`ModuleNotFoundError: No module named 'rs_backbone_eval.data'`。
- 修复：从原开发机恢复真实数据处理源码；将大文件目录忽略规则锚定在仓库根部，或精确放行源码目录；在干净 checkout 的 CI 中验证安装、CLI 和测试。

## 2. 影响公平性的实验设置

### 相同头部不代表相同监督条件

| 设置 | AnySat | Clay | Prithvi |
|---|---|---|---|
| T1 B1 默认 batch | 2 | 4 | 1 |
| T1 B1 weight decay | 1e-4 | 1e-4 | 0.05 |
| T1 训练空间采样 | 固定中心裁剪；报告 B1 用 224 | 固定中心 256 | B1 固定中心 256；B2 整景编码 |
| T5 B2 监督网格 | 原始标签网格 | 标签最近邻下采样至 28×28 | 标签最近邻下采样至 14×14 |
| T5 时序处理 | 主干原生融合 + 空间头 | 逐日期编码 + 时序头 | 逐日期编码 + 时序头 |
| T5 B2 日期进入任务头 | 使用读取的日期 | 缓存训练/评价路径全部置 0 | 使用读取的日期 |

表内 batch、weight decay、裁剪为当前代码默认值或文档记录；环境变量可能覆盖，必须通过 resolved config 确认每个历史 run 的实际值。

- **监督网格是最需要修正的混杂因素。** Prithvi T1 B2 在 `t1_frozen.py:226` 下采样标签；Prithvi T5 在 `t5.py:212`、Clay T5 在 `_labels_on_grid()` 中做同样处理。T5 的 14×14 标签仅有原始 224×224 的 1/256 个采样点，28×28 为 1/64；小地块和边界监督可能大量消失。评估时插值回原图不能补回训练期间丢失的标签信息。
- 建议统一在原始标签网格计算损失：先上采样 logits，再与完整有效标签计算 CE。各模型原生特征步长可以不同，但应记录；进一步做同特征网格消融，以区分空间分辨率与表征质量。
- **T5 当前排名不能独立归因于骨干。** 除时序架构差异，Clay 缓存路径还丢掉日期，Prithvi 关闭了原生联合时序处理。建议同一 B2 下拆两个 panel：统一逐帧特征+相同时间头；原生时序能力+明确的任务头。原生时间上下文与外部学习到的时间融合应单独解释。
- **同 epoch 不等于同优化预算。** 默认 batch 的差异导致每轮更新次数不同；没有梯度累积来对齐。主干与头共用 LR，也未普遍实现设计中的调度器与增强。应固定有效 batch、数据曝光量、验证次数，并报告实际 optimizer steps；相同搜索次数比强行相同 LR 更合理。
- **固定中心裁剪浪费监督。** 512→256 只覆盖约 25% 面积，512→224 约 19%，重复训练也不会看到其余区域。建议三家同步采用随机裁剪和水平/垂直翻转，多时相与标签同步变换。统一尺寸前先测修复后显存。
- **T5 不只是缩短 epoch。** 三个 worker 都使用不加权 CE；官方 sample YAML 还有类别权重、StepLR、不同 weight decay 与增强。当前可以称项目自定义预算协议，不能只以“20 vs 125 epoch”概括与官方配置的差异。[官方 multicrop 配置](https://github.com/NASA-IMPACT/Prithvi-EO-2.0/blob/main/configs/multicrop.yaml)

## 3. 数据、时间和缓存

- **空间划分需要实际审计，暂不能断言已泄漏。** T2/T5 测试用例把同一 tile 的样本按 90/10 分入训练和验证，表明目前并未通过这些测试保证 group-disjoint。恢复数据构建代码后，应检查原始景、相邻 chip、同一事件、跨日期同一区域的重叠。官方划分保留用于 benchmark，同时单独做地理 holdout，避免把同区域插值能力解释成跨区域泛化。
- **DOY 转换错误。** 多个 dataset 使用“距 1970 年天数 `% 365`”，这不是公历年内日期，会随闰年偏移。应统一按当年 1 月 1 日计算零起点 DOY，明确闰年约定并测试日期边界。[AnySat 官方接口](https://github.com/gastruc/AnySat)要求年内日期；预训练时间编码对此有实际语义。
- **元数据不对称。** Clay 编码器的 time/latlon 为零，Prithvi TL 的自定义调用未传位置/时间，AnySat 则传入日期。可以定义 metadata-off 统一对照和 metadata-on 原生能力对照，不能只使用 TL 权重就宣称完整利用了 TL 能力。
- **缓存键不完整。** Clay T5 的键只有 manifest 文件名、patch、chip size、split、样本数，没有 checkpoint、预处理、波长、代码版本。且 `path.is_file()` 就复用，提取中断留下的部分文件也可能被当作完成缓存。应加入完整哈希、shape/dtype、完成标记，写临时文件后原子提交。
- **归一化缓存同样需绑定 manifest。** 如 AnySat T1 仅检查 bands，修改训练划分后可能继续用旧统计量。
- **manifest 的“最新”选择错误。** `dispatch.py:57` 按哈希文件名排序并取最后一个，与生成时间无关。正式实验应显式指定 manifest 哈希，不依赖自动 latest。

## 4. 扰动协议、统计与报告解释

- D2 使用“归一化后补 0”。AnySat T1 的归一化来自训练集，但 Clay 使用官方元数据，Prithvi 使用数据模块常量；补 0 实际对应各自不同的原始值，未落实“所有模型用同一训练集均值填充”。建议先在统一物理输入域填充，再各自归一化，并保存实际填充值。
- `perturbations_from_env()` 和 band list 都用逗号分隔，显式传 `band_drop:NIR_NARROW,SWIR_1,SWIR_2` 时会被拆成三个实验，后两项退回 none。`default` 特殊入口不受此解析问题影响。改为结构化列表或用分号分隔实验，未知参数应报错。
- 不应把“丢更多波段必须更差”作为正确性验收：噪声、冗余和分布变化都可能导致非单调结果。应检查扰动确实生效，报告非单调现象与区间，而非修改到符合预期。
- D1 当前统一取 max；T7 RMSE 越低越好，会被反向排名。应读取 metric direction；聚合任务必须用各模型共同覆盖的集合。
- D3/D4 将最慢/最不稳定者强制映射为 0，容易夸大差异。建议优先展示原始 IoU、时间、显存及误差条，展示精度—成本 Pareto 关系，暂缓总分。
- 成本必须分开计时：首次特征提取、缓存复用后的头训练、验证、推理、超参搜索总量。Clay T5 缓存提取在计时之外，Prithvi T5 包含提取；两者不能直接比较训练 wall time。
- 三个 seed 的标准差不等于泛化误差的 95% CI。当前 `bootstrap_ci()` 计算样本指标均值的区间，而主指标是全局混淆矩阵计算的 IoU，两者统计目标不同。建议保存逐景混淆矩阵，按地理组/事件配对 bootstrap，每次重采样重新累计后计算全局 IoU 及模型差值。
- 自定义训练路径尚未普遍落盘最终模型、optimizer/RNG 状态和逐景混淆矩阵；`BestCheckpoint` 只保存在内存。优先补齐，以便独立评价、恢复和审计。
- `report.py` 大量叙述硬编码，已出现种子覆盖、任务进度与表格不一致；应从 run 元数据生成。当前阶段报告对 Prithvi 的差值解释也与表中数字不符，需重新核算。

## 5. 更有价值、也更省算力的下一轮

1. **先做训练语义验收。** 恢复源码、修 adapter 梯度、核对并解冻 Clay B1、前置 seed、修 B0 权重恢复和汇总规则。用小张量/单批次检查冻结、不冻结、适配器更新、相同 seed 重复运行和原始主指标选择；无需先跑完整数据。
2. **锁定 T1/T2 受控对比。** 统一 manifest、损失网格、训练 crop/增强、有效 batch 和验证规则；每模型相同验证搜索预算，选择超参后锁定。B1 先完成 3 模型×2 任务×3 seed=18 个最终运行，搜索运行单独计费。若算力紧张，可先完成 T1 的 9 个最终运行。
3. **重做 T5 的最小关键消融。** 修日期和标签监督，统一逐帧时间头做一组，原生时序能力另做一组。先单种子检查 20 epoch 学习曲线，再决定是否增加预算/种子。20 epoch 可以作为固定预算 benchmark，但不称能力上限。
4. **补强因果对照。** 同一 backbone 的预训练初始化 vs 随机初始化，才更直接回答预训练价值；小 CNN vs 大预训练 ViT 同时改变架构、容量和初始化，适合选型而非归因。再加一个轻量监督 CNN 作为实用基线。RGB/六波段分别重新训练，用于衡量信息增益；推理时屏蔽波段用于衡量鲁棒性，两个问题分开。
5. **性能优化后测证据。** 对纯冻结、固定输入的分支缓存一次特征并跨 seed/LR 复用；有可训练输入 adapter 时不能复用过期 backbone 特征。用混合精度、激活重计算和梯度累积控制显存。AnySat 的密集特征上执行 256 通道 3×3 卷积开销很大，可单列低分辨率头/轻量 decoder 消融。减少逐 batch 清空 CUDA cache 和重复读取影像前，先 profile 并确认对显存的影响。
6. **最后扩任务。** T1/T2/T5 的受控结果稳定后，再补 T4/T6/T7；当前先扩展所有任务会把相同问题复制进更多结果。
