# RTX 5090 夜间算力接入与 T10B2 补种子安排（2026-11-04）

本文记录新增 RTX 5090 机器的接入过程、已做的决策、数据布局和对 T10B2 夜间任务的安排。
它是**运行记录与决策提案**，不是结果报告；T10B2 的正式结论仍以 `run.json` 和审计为准。
文中"实测"均注明测量条件，"待验证"表示尚未完成、不能当结论引用。

## 1. 目的与范围

- 在不影响 4090 主队列的前提下，为一晚能跑完的 cell 增加一台夜间算力。
- 首个排期：T10B2（FAIR1M 旋转检测，冻结 LIM）的 **seed 17 / 42**，v8 配方。
- 不涉及评测口径、聚合规则或指标存储的改动；不改 `matrix.py` / `report.py` / `audit.py`，
  因此**不新增 `required_fixes`**。
- T11（PASTIS-HD）仍以 4090 为正式 cell，5090 不碰已有 `-4090` run。

banner 超时。事后确认是 WSL 磁盘写满导致的系统级故障（见 §4），不是 frp 配置问题。

### 2.1 公网暴露面

`superderp.cn:6004` 把 WSL 的 sshd 暴露在公网（frp 转发到 Windows，再进 WSL）。当前已核实：

- `PasswordAuthentication no`（`/etc/ssh/sshd_config.d/99-disable-password.conf`），只允许密钥登录；
- 未设置 `AllowUsers`，但登录用户只有 `yzhong`，且我们没有开 root 登录。

**决策 D1b：保留"仅密钥"现状；起跑前如需更严，加 `AllowUsers yzhong`，或干脆只保留
局域网入口、关掉公网中继。** 公网入口只是方便值班，不是数据通道。

## 3. 环境决策

### 3.1 CUDA 可用性（已完成，实测）

用 4090 的 uv 缓存离线安装 `torch==2.9.1+cu128` 后验证：

```
torch 2.9.1+cu128   cuda build 12.8
available True      device NVIDIA GeForce RTX 5090   capability (12, 0)
matmul 20 × 2048²   0.076 s
```

结论：5090 在 WSL2 下可直接用官方 cu128 wheel，无需自编译。

### 3.2 为什么复制 venv 而不是重新 `uv sync`

- `uv sync --offline --frozen` 在 5090 上无法完成离线解析（多次超时/缺包），
  在线装则要重新下载数 GB 的 CUDA wheel。
- T10 检测器是纯 torch/torchvision，**没有自定义 CUDA 扩展或 nvcc 编译**，
  所以 venv 可跨同架构机器复制。
- venv 里的绝对路径固定为 `/home/yzhong/projects/rs-backbone-eval`，因此仓库必须放在该路径，
  不能放在 `~/rs-backbone-eval` 再软链。

**决策 D2：复制 4090 的根 `.venv`（177 MB）与 `workers/lim/.venv`（6.8 GB），
并把仓库固定在 `/home/yzhong/projects/rs-backbone-eval`。**
若后续要长期维护这台机器，再改为每条 worker 独立 `uv sync`。

这一步有两个隐含前提，起跑前必须验证（review 2026-11-05）：

1. **系统 Python 版本一致**：`workers/lim/.venv/bin/python` 指向 `/usr/bin/python3`，
   5090 上实测为 **3.12.3**，与 4090 相同；
2. **仓库与 lock 一致**：`uv run --project workers/lim` 默认会校验环境与 lock，
   在 `UV_OFFLINE=1` 下 lock 不一致会直接失败。因此 5090 的仓库必须和 4090 在
   同一个干净提交上，并先跑：

```bash
uv run --project workers/lim --frozen python -c \
  "import lim_worker.t10, torch; print(torch.__version__, torch.cuda.get_device_name())"
```

仓库升级（依赖或 lock 变化）后，venv 必须重新复制，不能原地 `uv sync`。
复制 venv 是临时方案，不是长期维护方式。

## 4. 磁盘事故与恢复（必须记录）

第一次同步把 FAIR1M 的 99 GB 直接写进 WSL ext4：

1. VHD 在 C 盘动态增长，C 盘被写满（只剩约 2 GB）；
2. WSL 内出现系统级 I/O 错误：`/usr/bin/grep`、`/usr/bin/ps` 报
   `Input/output error`，`ps` 直接 `Bus error (core dumped)`；
3. 公网 SSH 表现为"端口可连、立即断开"，LAN SSH banner 超时——容易被误判为网络问题；
4. 处理：Windows 侧清出 150 GB → `wsl --shutdown` 重启 → 删除刚拷贝的数据 →
   `diskpart` 的 `attach vdisk readonly` + `compact vdisk` 压缩 VHD；
5. 恢复后 `df -h /` 为 131 GB 已用 / 825 GB 可用，`ps`、`grep` 正常，GPU 可见。

**决策 D3：大文件一律放 E 盘（NTFS，1.1 TB 空闲），不再写入 WSL ext4。**
ext4 只放仓库、venv、manifest、derived 标注和小权重；C 盘 150 GB 余量是硬约束，
VHD 只增不减，必须留出安全边界。

**教训**：WSL 的"磁盘满"不会表现为 `No space left on device`，而是二进制执行报
I/O error / Bus error；以后遇到同类症状先查宿主盘和 VHD 大小。

## 6. T10B2 夜间任务

### 6.1 为什么选 T10B2 的 seed 17 / 42

- T10B2 v8 是 2026-11-03 归一化决策后的首个 T10 配方
  （LIM 使用 ImageNet 预训练统计，`preprocessing_id=fair1m_rgb_imagenet`），
  三个 seed 在 4090 上都还没有跑过，是一个**全新空格**；
- 不覆盖、不改写任何已有 v7/v8 run；
- 单 seed 在 4090 上约 3.1 h（25000 optimizer steps，micro 1 × accum 2），
  5090 预计 2–2.5 h，一晚可完成两个 seed；
- seed 73 不在今晚：一晚塞三个 seed 会越过白天用机时间，且失败后没有重试余量。

**决策 D5：5090 只跑 `lim_mit_huge-T10-rotated_frozen-train-{17,42}-v8-5090`，
seed 73 另排，且必须仍在 5090 上跑完（同一 cell 不混 host / GPU class）。**
run id 带主机后缀，mirror 了 T11 的 `-4090`；若 5090 不可用、整个 cell 迁到别的机器，
后缀也要跟着换（新 cell），不能只补一部分 seed。

同名 run 的防重：两个账本互相不可见，dispatch 只检查本地目录是否存在。因此：

- `RS_EVAL_T10B2_SUFFIX` 在 lane 里是必填项，缺省直接报错；
- 4090 侧的 T10B2 lane 注释明确写"v8 已交给 5090，禁止在 4090 启动"；
- 回传使用 `rsync --ignore-existing`，已有目录一律不覆盖。

### 6.2 启动参数（与 `scripts/rerun_baselines.sh` 的 T10B2 lane 一致）

```
RS_EVAL_MANIFEST=$DATA/manifests/T10/holdout_1024_s824_seed17.jsonl
RS_EVAL_T10B2_SEEDS="17 42"
RS_EVAL_T10B2_SUFFIX=5090       # 必填；run id 以 -v8-5090 结尾
LIM_WORKER_TOTAL_STEPS=25000
LIM_WORKER_EPOCHS=12          # 仅循环上界，步数预算先触发
RS_EVAL_RERUN_STOP_ON_FAIL=1  # seed 17 出问题不烧掉 seed 42
```

manifest 固定为 `holdout_1024_s824_seed17.jsonl`；同一 cell 的各 seed 必须共享同一
manifest（sha256 会写进 `run.json`）。

worker 现在在 `run.json` 的 `tags` 里记录：

- `device`：`cuda` / `cpu`；
- `host`：GPU 型号（如 `nvidia-geforce-rtx-5090`），与 T11 的口径一致；
- `hostname`：实际主机名（如 `YZ-WORKPC`）；
- `torch`：运行时 torch 版本。

这样 4090 与 5090 的记录在账本里可直接区分，审计和 Portal 的耗时对比不会混 GPU。

### 6.3 结果回传与准入

1. 5090 的 run 先落在 `~/rs-eval/runs/`；
2. 完成后回传到主账本 `/geodata/rs-eval/runs/`，命令必须带 `--ignore-existing`：

   ```bash
   rsync -a --ignore-existing ~/rs-eval/runs/lim_mit_huge-T10-*-v8-5090/ \
     yzhong@192.168.1.89:/geodata/rs-eval/runs/
   ```

   **不手写、不修改、不覆盖 `run.json`**；目标已存在时保留旧记录并停下来人工核对；
3. 回传后跑 `scripts/audit_runs.py`，确认 `git_commit`、`host`/`hostname`、manifest 和预算；
4. 只有 `completed` + 官方步数 + 未被 superseded 的记录才进入报告与 Portal。

**已知限制：`request.json` 里的路径是 5090 本地路径**（`/home/yzhong/rs-eval/data/...`），
回传后在 4090 上无效。影响范围：

| 消费者 | 是否受影响 |
|---|---|
| 审计、报告、Portal | 否，只读 `run.json` |
| `visualize_run.py` / replay | 是，需要 manifest 与数据路径 |
| `--resume-from` | 是，但本 run 已完成后不需要续训 |

如果以后要在 4090 上给这批 run 生成图集，需要在 4090 上建相同路径的软链接
（或临时把 manifest `data_root` 指到对应位置），不要修改回传的 `run.json`。

**已知限制（续训）**：5090 上的 `training_checkpoint` tag 与 `latest.pt` 路径同样是本地路径；
跨机续训前必须先把 checkpoint 拷到目标机并显式传 `--resume-from`。

## 7. 9p 性能实测与影响评估

WSL2 的 `/mnt/e` 是 9p（drvfs），不是 ext4。实测（同步正在写盘，数字偏保守）：

| 操作 | E 盘（9p/NTFS） | WSL ext4 |
|---|---|---|
| 顺序读大文件 | 196 MB/s | 2.4 GB/s |
| 小文件 open/stat | 每次 open 都是 RPC，明显更慢 | 本地系统调用 |

T10 的读取模式与预算（review 2026-11-05 修正）：

- 每个样本 `rasterio.open()` 打开一张大 tif，再读 1024×1024 窗口；
- `holdout_1024_s824_seed17` 的 train 有 15389 个 tile、来自 11805 张图
  （平均 1.3 tile/图），**每张图每 epoch 基本只读一次，page cache 复用很低**；
- 真正的预算不是 12 个 epoch：`LIM_WORKER_EPOCHS=12` 只是循环上界，
  25000 个 optimizer step × 2 tile/step = **5 万个 tile**，约 **3.25 个 epoch**；
- 按每 tile ~3 MB 估算，训练读取约 **150 GB**，再叠加验证/测试；
- GPU 消耗速度：4090 实测 0.447 s/step、2 tile/step ≈ **4.5 tile/s**；5090 预计 6–8 tile/s。
  9p 顺序读 196 MB/s ≈ 65 tile/s，理论上不是瓶颈。

**验收标准（待验证）**：数据吞吐 ≥ GPU 消耗速度的 **1.5 倍**，且训练时 GPU 利用率 > 80%。
达不到再按下面顺序优化，不在未测量的情况下先搬数据：

1. `LIM_WORKER_NUM_WORKERS=8`（20 核 / 31 GB 足够）；
2. **不建议**把 54 GB 的 `images/` 拷到 WSL ext4：C 盘会降到约 96 GB，而 VHD 只增不减，
   风险和 §4 的事故同类；
3. 长期方案：把 WSL 发行版迁到 E 盘（`wsl --export` / `--import`），
   VHD 走 virtio-blk，不再受 C 盘 150 GB 限制。此项需要停机 1–2 小时，今晚不做。

## 9. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| C 盘/VHD 再次被写满 | WSL 系统级 I/O error，SSH 假死 | 大文件只放 E；监控 C 盘余量；VHD 定期 compact |
| 9p 随机读慢 | dataloader 拖住 GPU，单 seed 变长 | 先实测；§7 的 1.5× 标准与优化顺序 |
| 两个账本产生同名 run | 回传覆盖或记录分叉 | run id 带 `-v8-<host>`；4090 禁跑 v8；回传 `--ignore-existing` |
| 白天机器被占用 | 任务被中断 | T10 支持 epoch 边界 checkpoint，可 `--resume-from` 续训；只在夜间排长任务 |
| WSL 休眠/掉线 | 夜间任务中断 | 关闭 Windows 睡眠；断点续训兜底 |
| 5090 与本 cell 其他 seed 混 host | 违反"同 cell 同 host" | seed 73 也固定在 5090；若 5090 不可用则该 cell 整体迁移，不混跑 |
| run 只留在 5090 本地 | 账本缺记录 | 完成后立即回传并审计；本地目录保留到审计通过 |
| 公网 sshd（`6004`） | 暴露面扩大 | 已仅密钥登录；可加 `AllowUsers yzhong`，或只保留局域网入口 |
| venv 与 4090 的 Python/lock 不一致 | `uv run --frozen` 失败或静默错版本 | 起跑前做 §3.2 的 `--frozen` 导入检查；仓库保持同一干净提交 |
