## 0. 一页结论

1. **T11 BBF 的 8 epoch 是官方最低预算，不是上限。** 当前 8-epoch 全量微调 seed 17 为 0.3982，低于冻结 20-bin 的 0.4094；这更像“预算太短/学习率偏激进”，不像实现错误（encoder 573 个张量全部更新，checkpoint 已保存）。
2. **先做 8-epoch 学习率筛选，再跑 20 epoch。** 筛选 `backbone_lr = 5e-5 / 1e-5`，对照现有 `1e-4`；每个条件 3 seed，避免单 seed 噪声。
3. **20 epoch 作为独立的 `BBF20` 轨**，不和 8-epoch `BBF` 混在一个 cell。筛出的最佳 LR 写进 `lim_s2_20bin_finetune_20ep.yaml` 后再起跑。
4. **50 epoch 不通过“20 epoch 续训”实现。** 当前 BBF 只保存最终权重，没有 optimizer/RNG；即使补 `latest.pt`，现有准入规则也不允许把 20-epoch checkpoint 续成正式 50-epoch 结果。50 epoch 应作为新的 `BBF50` 轨从头跑，或明确标为“暖启动实验”，不与正式 50-epoch 结果混用。
5. **5090 最适合补 AnySat T3/T4 B1。** 4090 上这两个 cell 的失败原因是 23.35 GiB / 23.52 GiB 的 OOM；5090 有 32 GB，数据与权重转移约 17 GB，收益明确。
6. **3080 继续 T9B2P seed 42 resume3**，不安排新任务，避免再次打断长跑。

## 2. T11 BBF：为什么要探索学习率和预算

### 2.1 8 epoch 的来历

- T11 官方套件（冻结表/AEF 表）预设 8 epoch，`matrix.OFFICIAL_EPOCHS["T11"] = 8` 是**最低正式预算**。
- BBF 最初按 8 epoch 排，是为了和冻结 20-bin 表在**同一预算**下直接对照。
- 8 epoch 对 1,455 个训练 patch、524M 参数的 MiT-Huge 全量微调偏短：只有 1,456 次 optimizer step。

### 2.2 当前 8-epoch 结果

| 条件 | seed | validation mIoU | test mIoU |
|---|---:|---:|---:|
| BBF 8ep，head 1e-3 / backbone 1e-4 | 17 | 0.3958 | 0.3982 |
| 冻结 20-bin | 17 | 0.4173 | 0.4094 |
| 冻结 20-bin | 17/42/73 均值 | — | 0.4131 ± 0.0050 |

实现正确性核查：

- `trainable_parameters = 532,062,996`，不是只训头；
- encoder 573 个参数张量与预训练 `mit_huge_600.pth` 全部不同（`exact equal 0/573`），说明骨干确实在更新；
- validation/test 由同一份 manifest、同一 20-bin 输入、同一 8 epoch 预算得到；
- checkpoint 同时包含 `encoder_state_dict` 和 `model_state_dict`。

因此当前结论是：**不是“骨干被冻住”或“权重没接上”，而是 8 epoch + 1e-4 骨干学习率可能不适合这个数据规模。**

## 3. 学习率筛选方案（8 epoch）

### 3.1 条件

| 条件 | head LR | backbone LR | epoch | seed |
|---|---:|---:|---:|---|
| 基线（已有） | 1e-3 | 1e-4 | 8 | 17/42/73 |
| LR-5e-5 | 1e-3 | 5e-5 | 8 | 17/42/73 |
| LR-1e-5 | 1e-3 | 1e-5 | 8 | 17/42/73 |

- 每个条件都是独立 protocol id，LR 写进配置，不使用环境变量覆盖。
- 三个条件都落在 `BBF` 轨，属于同一 cell 的超参网格；`build_matrix` 只用 validation 选一个变体，test 不参与选择。
- 选模只看 validation；最终报告保留三个变体的完整结果。

### 3.2 时间

- 单个 8-epoch run 约 35 min；
- 新增 2 个 LR × 3 seed = 6 run，约 **3.5 h**；
- 4090 在 BBF 8-epoch 三 seed 结束后开始，预计 **17:20 左右**完成。

## 4. 20 epoch 方案（BBF20）

### 4.1 口径

- 新 protocol：`lim_s2_20bin_finetune_20ep`，`epochs: 20`；
- 新轨道：`BBF20`，**不与 8-epoch `BBF` 同 cell**；
- 训练配方与 BBF 相同：20-bin LTAE2d、有效 batch 8（micro 1 × accum 8）、`checkpoint_frames=20`；
- 最佳 backbone LR 由第 3 节筛选决定，写入 20ep 协议后再起跑；
- 每个 run 保存 `final_checkpoint.pt`。

### 4.2 时间

- 按实测约 4.4 min/epoch，20 epoch ≈ 1.5 h/seed；
- 3 seed 约 **4.4 h**，预计 **22:00 左右**完成。

### 4.3 为什么现在先跑 20，而不是直接 50

- 20 epoch 是低成本的中间点，可以先确认“预算增加是否真的改善”；
- 如果 20 epoch 仍低于冻结头，直接上 50 epoch 的收益需要重新评估；
- 20 epoch 的结果也可以帮助判断是“欠训练”还是“学习率破坏预训练特征”。

## 5. 50 epoch 方案（备选，需单独批准）

### 5.1 口径

- 新 protocol：`lim_s2_20bin_finetune_50ep`，`epochs: 50`；
- 新轨道：`BBF50`，与 `BBF` / `BBF20` 完全分开；
- 从头训练，不使用 20-epoch 权重做正式续训；
- 预计 3.7 h/seed，3 seed 约 **11 h**，可过夜。

### 5.2 为什么不做“20 → 50 续训”

当前 BBF：

- 只保存最终权重 `final_checkpoint.pt`，没有 optimizer state、RNG state、epoch 进度；
- T11 worker 没有 `resume_from` 路径；
- 即使补 `latest.pt`，现有 `TrainingCheckpoint` 的身份校验包含 `settings["epochs"]`，20-epoch checkpoint 不能直接作为 50-epoch 正式 run 续训；
- 项目准入规则明确禁止把短预算 checkpoint 续成正式预算，避免“smoke 变正式”。

可选方案：

1. **推荐**：50 epoch 从头跑，作为独立 `BBF50` 轨；
2. 如确需省算力：做“20 epoch 权重 + 新 optimizer + 再训 30 epoch”的暖启动实验，单独命名、单独轨道、在报告中注明“不等于连续 50 epoch”，不作为正式 50-epoch 结果。

## 6. 5090：AnySat T3/T4 B1 补跑

### 6.1 为什么选这两个 cell

主账本中：

```
anysat_base-T3-full_finetune-{17,42,73}-v6  failed
OutOfMemoryError: 23.35 GiB in use / 23.52 GiB total
```

T3 只差约 300 MB 就放不下；5090 有 32 GB，预计可以直接过。T4 也缺 AnySat B1，可与 T3 共用同一份 AnySat 权重。

### 6.2 需要同步的资源

| 资源 | 大小 | 说明 |
|---|---:|---|
| AnySat checkpoint | 481 MB | `/geodata/rs-eval/weights/anysat/base` |
| T3 burn_intensity | 1.7 GB | raw 数据 |
| T4 landslide4sense | 8.5 GB | raw 数据 |
| T3/T4 manifests | < 3 MB | `data/manifests/T3`、`T4` |
| AnySat worker venv | 5.5 GB | 优先从 4090 复制，避免 5090 访问外网 |
| 合计 | 约 16 GB | 5090 剩余约 771 GB |

### 6.3 口径

- 全部 seed 都在 5090 上跑，不拆 host；
- 有效 batch 2：`micro 1 × accum 2`；
- B1 训练裁剪 224 px；
- 先跑 seed 42 验证 32 GB 能过，再跑 17/73；
- 每个 cell 的 run id 带 `-5090` 后缀，完成后按 host 一致性检查回传主账本。

### 6.4 时间

- T3 其他模型的 B1 在 4090 上约 0.13–0.39 h/seed，AnySat 预计 1–2 h/seed；
- T4 其他模型约 2.4–3.1 h/seed，AnySat 预计 3–4 h/seed；
- 三 seed 合计约 **12–18 h**，可与 4090 的 T11 实验并行。

### 6.5 5090 不安排的事项

- **T11 BBF / LR 筛选**：PASTIS-HD 约 81 GB + AEF features 5 GB，传输成本高；且不同 host 会与 4090 的 BBF cell 混淆，不适合做 LR 对照。
- **T9 LIM B1U**：需 iSAID 约 34 GB，25k steps 很长，优先级低于 T3/T4。
- **T5 AnySat B1**：125 epoch + 24 GB 数据，优先级更低。

## 10. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 5090 T3/T4 仍 OOM | 先跑 1 个 seed；保持 micro 1 × accum 2、224 crop；若仍 OOM，记录峰值并回退到 T3 seed 42 单点，不静默改 batch |
| 5090 无 AnySat venv / 无法访问外网 | 从 4090 复制 `workers/anysat/.venv`；代码用 git bundle 同步，不依赖 GitHub |
| 数据同步不完整 | `rsync --checksum`；正式 run 前固定 `RS_EVAL_MANIFEST`，并跑 `audit-data` |
| 4090 磁盘不足 | 每个 seed 完成后把 `final_checkpoint.pt` 传到 NAS/5090；不删除 `run.json`、日志或 run 目录 |
| LR 筛选过拟合 validation | 三个变体都保留完整 test 结果；选模只用 validation；报告写明网格与选择规则 |
| 8/20/50 混 cell | `BBF` / `BBF20` / `BBF50` 三个 track 分离；显式预算轨写 `epochs_budget`，8-epoch 基线不写该 tag 以保持三 seed 同 variant |
| 3080 再次卡死 | 保持当前单任务；若再次不可 kill，重启后从 epoch 边界 resume，不把 smoke checkpoint 续成正式预算 |
| 5090 host 标签缺失 | 正式 run 前确认 `host`/`hostname` tags；同一 cell 不混 4090/5090 |

## 11. 验收标准

- 所有正式 run `status=completed`，`run.json` 的 `git_commit` 不带 `-dirty`；
- `run.json.artifacts` 包含 `final_checkpoint.pt`（BBF/BBF20），文件可读、大小符合预期；
- `uv run python scripts/audit_runs.py /geodata/rs-eval/runs .` 对新增 run 判定通过；
- 同一 cell 的 seed 全部在同一 host/GPU class；
- 报告里 `BBF`、`BBF20`、`BBF50` 分开成行，T3/T4 AnySat B1 进入对应 cell；
- 5090 的 T3/T4 run 明确标记 `host=nvidia-geforce-rtx-5090`，回传后主账本与 5090 账本一致。
