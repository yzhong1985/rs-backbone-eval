# 实验执行方案 v3.4 补充：T13 全量微调（FT）对照

- 日期：2026-11-19
- 状态：代码、配置与 CPU 测试已完成；尚未在 GPU 上运行，显存与时长均为估算（见第 6 节）。
- 原文 `实验执行方案_v3.4.md` 未改动。本补充只新增一个门禁，不改变 v3.4 的任何门禁。

## 1. 为什么加 FT

上级建议把冻结与全量微调做成 2×2 对照。现有的 B0 与 R（`whu_b0`、`whu_r`）冻结 LIM，只能回答“头和注入器在冻结主干上能学到多少”。全量微调回答另一个问题：主干在训练中能否吸收 AEF 信息，以及 AEF 增益在解冻后是否还在。

主要报告增益是 **FT-R − FT-B0**，即全量微调下 AEF 注入的增益。

## 2. 与 v3.4 第 4.1 节的关系

- v3.4 第 4.1 节的推进顺序（`G0a` 至 `G5`）不变，每个门禁的放行证据不变。
- v3.4 在“只换特征插件”的交付模式下要求公共 `LIM` 底座冻结（第 17 行的交付边界）。FT 两组解冻 `LIM`。这是对“共享冻结底座”规则的显式例外，只用于本对照，不改变已有的部署路线。
- 新增门禁 **`G1-FT`**：FT-B0 与 FT-R 各自完成 seed 17、42、73 三个正式 run（`completed`、官方 20 epoch、未 superseded），并给出逐 seed 的成对差值表（FT-R − FT-B0，以及 FT-B0 − B0、FT-R − R）。`G1-FT` 不是 `G2` 的前置条件。
- FT 结果不替代冻结路线的交付结论。要把 FT 作为交付路线，需要单独的决策。

## 3. 四组定义

| 组 | 协议 ID | 主干 | 头 | AEF 注入器 | 输入 | 损失 | 报告轨道 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| B0 | `whu_b0` | 冻结 | 训练 | — | RGB（3 ch） | CE | `W0`（诊断） |
| R | `whu_r` | 冻结 | 训练 | 训练 | RGB + 真实 AEF | CE | `WR`（诊断） |
| FT-B0 | `whu_ft_b0` | 训练 | 训练 | — | RGB（3 ch） | CE | `WF0`（诊断） |
| FT-R | `whu_ft_r` | 训练 | 训练 | 训练 | RGB + 真实 AEF | CE | `WFR`（诊断） |

- AEF 只输入 R 与 FT-R。部署时 R 与 FT-R 都需要 AEF，属于参考路线。
- 四组都进入 `DIAGNOSTIC_TRACKS`，不进入 headline、scorecard、Pareto 或 Portal 的主表，直到某个门禁提升它们。

## 4. 读法

所有比较都在同一 seed 内配对，然后汇总三个 seed。

- 冻结下的 AEF 增益：R − B0。
- 全量微调下的 AEF 增益（主要报告增益）：FT-R − FT-B0。
- 微调本身的增益：FT-B0 − B0，以及 FT-R − R。
- 交互项：(FT-R − FT-B0) − (R − B0)。若交互项接近 0，AEF 增益不依赖主干是否解冻。

报告每组的 `mean ± std` 与三个 seed 的逐对差值。不把 seed 42、73 的结果与 seed 17 单独挑出来比较。

## 5. 训练配方

- 头与注入器学习率 `learning_rate = 0.001`；主干学习率 `backbone_learning_rate = 0.00005`。这与 `configs/protocols/lim_s2_20bin_finetune_lr5e5.yaml` 相同。这两个值没有在 T13 上做扫描，结论依赖这一固定配方。
- 20 epoch，`warmup1-cosine`，AdamW，weight decay 1e-4。
- 有效 batch 8。FT 的默认 micro batch 为 2、梯度累积为 4；可以用 `LIM_WORKER_MICRO_BATCH` 与 `LIM_WORKER_GRAD_ACCUM` 覆盖，有效 batch 必须仍为 8。
- 数据划分、增广、验证频率（每 5 epoch）、按验证集 `mean_iou` 选模、测试集只评一次：与 `whu_b0`、`whu_r` 完全相同。
- 精度：CUDA 上主干为 fp32 权重加 bf16 autocast，不使用 GradScaler。选 bf16 的理由：4090 与 3080 同为 Ampere 或 Ada，bf16 张量核心吞吐与 fp16 相同；bf16 的指数位与 fp32 相同，MiT 注意力 logits 不会溢出；不需要动态损失缩放。CPU 上关闭 autocast，测试在 fp32 下运行。
- 梯度检查点（每个 MiT block）默认关闭，用 `LIM_WORKER_GRAD_CHECKPOINT=1` 打开。打开后每步多一次编码器前向，显存大幅下降（见第 6 节）。

## 6. 内存与时间

### 6.1 实测值（只读，未改动任何 run）

数据来自 `/geodata/rs-eval/runs/lim_mit_huge-T13-whu_b0-train-17-v2/run.json`，这是冻结 B0 的一次正式运行。

- `train_seconds` = 5249.4 s，`wall_time_seconds` = 5405.3 s，20 epoch。
- `optimizer_steps` = 27000，即每 epoch 1350 步（10,800 块 tile、micro 8、无累积）。每个 8 tile 步约 0.194 s，包含冻结编码器的 fp16 前向、头的前向与反向、数据加载，以及四次验证。
- `trainable_parameters` = 6,954,760（头）；`total_parameters` = 531,389,704。由此得到 MiT-Huge 编码器参数量 **524,434,944**（两者之差）。
- `peak_gpu_memory_mb` = 3743 MiB（冻结、fp16、micro 8、无梯度）。这个数不能外推到微调。

### 6.2 估算（未在 GPU 上测量）

假设：
- AEF 注入器的参数量由模块定义手算：两层深度注入器（1024 与 2048 通道，隐层 128，输入 64）共 413,184 个参数。
- 静态显存按 fp32 权重、fp32 梯度、AdamW 两个状态（fp32）计算，另加一份 bf16 的自动混合精度权重缓存。
- 激活显存的单样本估计：MiT 每个 token 每个通道约保存 18 个张量，注意力图按 sr 缩减后的 key 数计算，并按 bf16 为 2 字节、LayerNorm 与残差保留 fp32 的部分乘 1.4 修正；头部 UPerNet 在 128×128 分辨率上约 0.3 GiB。合计约 2.7 GiB/样本，区间 2.0–3.5。
- 梯度检查点时，每个样本保存各 block 的输入（约 0.08 GiB）加头部（约 0.3 GiB），重算时单个最大 block（stage 1）约 0.2 GiB/样本。合计约 0.58 GiB/样本。

静态显存（GiB）：

| 项目 | 计算 | GiB |
| :--- | :--- | ---: |
| 编码器 fp32 权重 | 524,434,944 × 4 B | 1.95 |
| 编码器 fp32 梯度 | 同上 | 1.95 |
| AdamW 两个状态 | 2 × 同上 | 3.91 |
| bf16 自动混合精度权重缓存 | 524,434,944 × 2 B | 0.98 |
| 头与注入器（权重、梯度、两个状态） | 7,368,000 × 16 B | 0.11 |
| 合计 | | 约 8.9 |

峰值显存（GiB），估算：

| micro batch | 无梯度检查点（激活 2.7 GiB/样本） | 无梯度检查点，区间 | 梯度检查点（0.58 GiB/样本） |
| ---: | ---: | :--- | ---: |
| 1 | 11.6 | 10.9–12.4 | 9.5 |
| 2 | 14.3 | 12.9–15.9 | 10.1 |
| 4 | 19.7 | 16.9–22.9 | 11.2 |
| 8 | 30.5（超出 24 GiB） | 24.9–36.9 | 13.5 |

4090 的显存为 24,564 MiB，约 23.99 GiB。扣除 CUDA 上下文与碎片约 0.7 GiB 后，可用约 23.3 GiB。

### 6.3 时长（估算）

- 冻结 B0 的实测每步时间为 0.194 s。假设冻结的编码器前向约占 0.15 s。
- 微调每步的估计：编码器前向加反向约为前向的 3 倍，即 0.45 s；micro 2 时 GPU 利用率较低，乘以 1.3–2.0 的修正，得到 0.6–0.9 s/步。
- 每 epoch 1350 步，即 13.5–20 min。20 epoch 加上验证（8 张验证图幅，4 次；20 张测试图幅，1 次）约 0.2 h，单个 run 约 4.5–7 h。
- 梯度检查点会多一次编码器前向，单个 run 约 6–9 h。
- 6 个 run（2 个协议 × 3 个 seed）顺序执行，无梯度检查点约 27–42 h，有梯度检查点约 36–54 h。
- 估计与实测的倍数关系（微调 / 冻结）约为 3–4 倍。这是由上面的成本模型推得的，不是测得的。

### 6.4 结论

- **4090 24 GiB 能跑。** 默认 micro 2、累积 4，无梯度检查点，估计峰值 14.3 GiB，余量约 9 GiB。
- micro 4 无梯度检查点估计 19.7 GiB，区间上限 22.9 GiB，接近卡的上限。在一次 smoke run 实测 `peak_gpu_memory_mb` 之前，不作为默认值。
- micro 8 必须开梯度检查点（估计 13.5 GiB），是 micro 2 之外的备选。
- **不需要 5090 来满足显存。** 5090（32 GB）能跑 micro 4 无检查点，并可能缩短墙钟时间（估计 1.3–1.5 倍，未测）。如果 5090 空闲且不与队列冲突，可以用它加速。
- **不建议 3080（20 GB）。** micro 2 估计 14.3 GiB 可以放下，但余量很小，而且 3080 不能访问 GitHub，只能靠 git bundle 同步代码。
- 磁盘：每个 run 的 `best_full_checkpoint.pt` 约 2.13 GB（编码器 fp32 2.10 GB 加头与注入器），6 个 run 约 12.8 GB，位于 `runs_root` 内。

## 7. 需要的 GPU 与运行顺序

1. 在 4090 上先跑一次 smoke（`LIM_WORKER_LIMIT_BATCHES` 与 `LIM_WORKER_EVAL_IMAGES` 设置为小值，notes 带 `SMOKE`，不会进入正式结果）。记录 `peak_gpu_memory_mb`、每步时间，并用实测值替换第 6.2 节的估算。这一步之前不决定 micro batch 是 2 还是 4。
2. 正式 run 放在 G2 队列清空之后，或者在空闲的 5090 上运行。FT 的 run 不与其他 lane 同时占用同一张卡。
3. 顺序：先跑 seed 17 的 FT-B0 与 FT-R（能尽早看到第一对成对差值），再跑 seed 42、73。同一个 cell 的 seed 留在同一台机器、同一种 GPU 上。
4. 通过 `uv run rs-eval dispatch` 或文件队列创建 run，不手写 `run.json`。在 run 的 tags 中可以找到 `arm`、`regime=full_finetune`、`backbone_learning_rate`、三项 `trainable_parameters_*`、`amp`、`gradient_checkpointing`、`micro_batch`、`grad_accum`、`peak_gpu_memory_mb`。
5. 本补充不要求任何 audit 修复 commit：新协议不改变已有 run 的存储指标值，因此 `required_fixes` 不需要增加条目。
