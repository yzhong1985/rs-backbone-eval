## 2. 先修掉的一个真问题：T10 把主干存了两遍（`caba2ab`）

`LimDetector` 同时把 MiT-Huge 注册为 `self.encoder`，又把它作为
`RotatedFasterRCNN(encoder, ...)` 的 `backbone` 注册了一次。PyTorch 的 `state_dict`
按模块路径展开，于是同一个主干在 checkpoint 里出现两次：

```
encoder.*            524.4 M 参数
detector.backbone.*  524.4 M 参数  ← 同一份权重
detector 其余         18.1 M
合计                1066.9 M 参数 = 3.97 GiB → 文件 4.11 GB
```

改成 `encoder` 只读属性（`detector.backbone`）后，同样的模型是 **542.5 M 参数 /
2.02 GiB**，实测 `latest.pt` 从 **4.11 GB 降到 2.16 GB**（3080 上 `-dedup1`），
两个 smoke 的 loss 与改前逐位相同（`7.6483` / `16.3189`），续训验证通过。

**注意**：`caba2ab` 之前的 T10 checkpoint 键名不同，当前代码**无法加载**；目前只有
smoke（`resumeB/D/F/G`、`smoke3`、`thr1-*`），没有正式 run 用过这些文件。

其它主干没有这个问题：Prithvi T9 1.21 GB ≈ 300 M 参数，单一注册；Anysat B1 1.99 GB
同理。静态检查方式：`sum(p.numel() for p in model.state_dict().values())` 应等于
`sum(p.numel() for p in model.parameters())`。

## 3. 为什么 checkpoint 一定包含冻结主干

`TrainingCheckpoint` 保存的是完整 `state_dict` + optimizer 状态 + RNG + `run_record`，
目的是"断电后接着跑"而不是"只存可训练部分"。冻结主干虽然不更新，但：

- 冻结 ≠ 不参与前向；续训时若只存可训练参数，必须保证重建路径与原来完全一致
  （同一 `PRETRAINED_CHECKPOINT`、同一 `in_chans`、同一 `drop_path`），否则重启后
  的模型与原 run 不是同一个函数；
- `best` 选择在 `select=True`（微调轨）时会额外持有**一整份**模型状态，所以 B1D 的
  checkpoint 约为 B2D 的两倍。

因此"冻结时只存可训练参数"不是无害优化，它把"可复现"换成了"依赖重建路径正确"。

## 5. 候选方案

### A. run 完成后删除该 run 的 `latest.pt`（推荐）

- **语义**：`latest.pt` 只在"还需要续训"时有价值。run 一旦 `completed`，续训需求消失；
  `run.json`、`best_checkpoint.pt`、日志、`checkpoints/` 里的其它产物全部保留。
- **收益**：4090 立刻回收 27.2 G（含 4 个已不可加载的旧格式 T10 文件），3080 回收 18.9 G；
  之后每个完成的 run 不再长期占 2–4 G。
- **风险**：无法"回头再续一个已完成的 run"（实际上也不需要：完成了就不该续）。
- **实施**：`scripts/prune_checkpoints.py --completed-only [--dry-run]`，只删
  `latest.pt`/`latest.pt.tmp`，逐条写 `runs_root/../checkpoint_prune.log`（审计轨迹），
  默认 dry-run；**不删 run 目录、不动 run.json**，与 AGENTS 的"run 目录不删"不冲突。
  需要同时在 AGENTS 写一句规则，否则下次审查会被当成违规删除。

### B. 冻结轨只存可训练参数 + 重建主干

- **收益**：LIM T10 B2D 从 2.16 G 降到约 0.25 G（18 M 参数 + optimizer）。
- **代价**：`TrainingCheckpoint` 需要区分"完整/增量"两种格式，续训时必须用 identity 里
  的 `pretrained_checkpoint` 重建主干并校验哈希；任何一处不一致就会变成"静默换了模型"。
- **结论**：现在不做。除非冻结轨的矩阵规模继续扩大，且 A 仍不够。

### C. 不动，扩盘

- 73 G 余量对完整矩阵（多主干 × 2 轨 × 3 种子）不够；且 3080 侧只有 63 G。
- 若扩盘，仍需回答 A 的规则问题，只是延后。

### D. 把 checkpoint 换到别的盘/NVMe（`RS_EVAL_CHECKPOINT_ROOT`）

- 现有实现**仍会在 run 目录写一份 `latest.pt`** 再复制到 `durable_path`，所以不能让
  run 目录"零 checkpoint"；只适合"镜像到更可靠的盘"，不适合省空间。
- 若采用 A，则 D 的必要性也随之下降。
