## 2. 统一头与输入路径

### 2.1 统一头：自研 torch-only UPerNet（不依赖 terratorch）

**为什么不用 terratorch**：

- `terratorch/models/decoders/utils.py:43` 的 `ConvModule` 把 `nn.BatchNorm2d` 写死，无法换成 GroupNorm；
- terratorch 只装在 `workers/prithvi` 环境，LIM/AnySat/Clay/Olmo 都没有，若要用就得给每个 worker 加依赖；
- `heads.py` 是控制层共享模块，不应反向依赖某个 worker 的框架。

**做法**：在 `src/rs_backbone_eval/heads.py` 增加一份**只依赖 torch** 的 UPerNet（PPM + FPN + 分类头），`norm_layer` 可配置（GroupNorm 默认），各 worker 共用；terratorch 的实现只作为对照参考，不引入依赖。

**验收**：单测覆盖 4 级输入形状、通道数不匹配、`num_classes=16`、参数量统计；`head_id` 记为 `upernet_gn`，与既有 `upernet_decoder`（B0 的 terratorch 实现）区分开。

### 2.2 归一化与有效 batch（统一口径）

| 项 | 决定 | 说明 |
|---|---|---|
| 头的归一化 | **GroupNorm** | BN 的统计依赖 batch 大小；有效 batch 8 也远小于 BN 通常需要的量级，GN 与 batch 无关，最稳 |
| 有效 batch | **8**（micro 1 × accum 8） | 这是 iSAID **本任务单独**的口径，不沿用其他任务的 2；所有主干必须一致 |
| 记录 | 写进协议与 `run.json` tags | `micro_batch` / `grad_accum` / `effective_batch` / `norm_layer` |

更正 v2 的错误：同事那边是 **SyncBN、batch 12 分布在 6 卡**，BN 统计来自 12 个样本，**不是**"单卡等效 batch 2"。他们能这么跑是因为 SyncBN 跨卡聚合统计量——我们单卡无法复现，所以才改用 GN。

### 2.3 更正：现有轨道并非都用一个头

| 头 | 用在 |
|---|---|
| `lite_spatial_head` | T1 / T1S / T4 / T8 |
| `temporal_segmentation_head` | T3 / T5（多时相） |
| `+spectral_adapter` / `+band_adapter` | AnySat / T8 的输入适配 |
| `upernet_decoder` | Prithvi B0 参考协议 |

因此"统一 UPerNet"是**新增一条头 + 新轨道**，不是替换某个既定头。

### 2.4 各主干的输入路径（v2 的缺口）

统一头之后，真正决定"客场有多不利"的是**每个主干怎么接收 0.3–1 m 的 3 通道 RGB**。逐主干如下：

| 主干 | 通道处理 | 元数据 | 四级金字塔来源 | 记录字段 |
|---|---|---|---|---|
| **LIM（MiT-Huge）** | 原生 3 通道，无适配 | 无（不需要） | **原生 4 级**（H/4、H/8、H/16、H/32） | `preprocessing_id=isaid_rgb_native`；`head_id=upernet_gn` |
| **Prithvi** | 3 → 6 通道：用 **1×1 卷积适配器**合成缺的 NIR/SWIR1/SWIR2（**禁止补零**，沿用 T8 的做法） | 无（Prithvi 不传 GSD/日期） | ViT token 抽层（300M 用 `[5,11,17,23]`，与 B0 一致） | `head_id=upernet_gn+band_adapter` |
| **Clay** | 3 通道直接给，波长填 0.48 / 0.56 / 0.655 µm | **GSD 元数据**：优先用 DOTA 元信息里的 `gsd`；缺失时按声明值填（默认 1.0 m，需在协议里写死） | 8×8 patch token 抽 4 层 + reshape | `preprocessing_id=isaid_rgb_clay_wl`；tags 记 `gsd_source`、`wavelengths_um` |
| **OlmoEarth** | 3 通道放到 S2 12 波段张量的 B02/B03/B04 位置，其余按 T1 的**填充规则**（band-set 只部分存在时必须填充、不能标 MISSING） | 无 | 稠密 token `[B,PH,PW,T,BS,D]`，对 T/BS 池化 | `preprocessing_id=isaid_rgb_olmo_fill`；tags 记 `filled_bands` |
| **AnySat** | 走 **`s2` 入口**（固定 10 波段），用光谱适配器把 3 通道映射进去 | **GSD 解释**：入口按 10 m 处理，而 iSAID 是 0.3–1 m；T8 已出现过"4 m 当 10 m"的问题，这次差距更大 → 必须记 `gsd_assumed=10`，并在结论里说明这是客场不利因素 | token 展平顺序特殊，需逆向 reshape（**风险最高**） | `preprocessing_id=isaid_rgb_anysat_s2`；tags 记 `gsd_assumed` |

**必须写进报告的推论**：这五种输入路径的"不利程度"不同（AnySat 与 Prithvi 需要合成通道，Clay/AnySat 还要处理 GSD 语义），所以结果只能读作"**在各自最自然的接入方式下的水平**"，不能读作"架构优劣"。这一点比 home/away 更影响解释。

## 3. 接入框架的改动清单（含 registry schema）

**为什么必须新开 protocol**：轨道由 `protocol_id` 决定（`matrix.py:19`）；`variant_key()`（`matrix.py:59`）已把 `head_id` 编进 key，所以 UPerNet 与轻量头的 run **不会混成同一条**，但 `_rank()`（`matrix.py:252`）仍会在**同一轨道内**按验证分挑 headline → 若 UPerNet 复用 `full_finetune`，它会把 B1 的 cell 顶掉。因此**必须新协议 → 新轨道**。

| 文件 | 改动 |
|---|---|
| `src/rs_backbone_eval/registry.py` | **`ProtocolSpec` 是 `extra="forbid"`，`regime` 是 Literal**，写不进 head/batch/BN。两种做法见下 |
| `src/rs_backbone_eval/heads.py` | 新增 torch-only UPerNet（§2.1） |
| `configs/protocols/*.yaml` | 新增 `upernet_frozen.yaml` / `upernet_finetune.yaml` |
| `matrix.py` | `PROTOCOL_TRACKS`、`TRACK_NAMES`、`TRACK_ORDER`、`OFFICIAL_EPOCHS`；`scorecard()` 里写死的 B1/B2 逻辑（约 `matrix.py:681`） |
| `report.py` / `portal/app.py` / `web/` | 新轨道展示与"最强单元"选择 |
| `configs/tasks/T9_isaid.yaml`、`configs/models/lim.yaml` | 新任务 / 新模型 |
| 各 worker `runner.py` | 任务允许列表（目前是硬编码集合） |
| `tests/test_registry.py` | 精确集合断言 |
| `tests/test_review_fixes.py`、`test_scorecard.py`、`test_portal.py`、`test_report_sections.py` | 轨道回归 |

**registry 的两种做法**：

| 做法 | 代价 | 评价 |
|---|---|---|
| A. 扩 `ProtocolSpec`（加 `head_id` / `norm_layer` / `effective_batch`），并把它加进 Literal regime 之外的结构 | 改 schema + `test_registry`，但语义最清楚 | 若以后还要加头，值得做 |
| B. 不动 schema：新协议只表达"轨道"，`head_id` / `norm_layer` / batch 全放 `tags`，靠 `variant_key` 已有的 `head_id` 轴区分 | 零 schema 改动 | **本版推荐**，先用这条把第一轮跑通 |

## 4. 协议设计

### 4.0 轨道：先冻结主干（B2U）

第一轮只**冻结主干、训练头**：

- 成本：只反传头，显存/时间降一个数量级以上（全量微调在 1024² 下是"数周/种子"量级）；
- 口径：与现有 B2 一致，是合法读数；
- 代价：分数会明显低于全量微调，**不能与 LIM 对外的全量微调数字直接比**；
- 后续：B1U（全量微调）作为单独决策，不在本版排期内。

### 4.1 划分：从 train 按原图切 validation

框架在 **validation** 上选 checkpoint（`selection.py`），测试集只报一次。iSAID 只有官方 train/val，val 要留作考试题，因此：

```bash
uv run rs-eval holdout-manifest \
  --manifest <isaid train manifest> --out <isaid manifest> \
  --split validation --source train --fraction 0.12 --seed 17
```

**前置条件**：manifest builder 必须把**原图编号**（如 `P0000`）写进 `group_id`，否则 `--fraction` 切的是"块"而不是"图"，同一张图的块会跨 split 泄漏。

### 4.2 组泄漏：**未排除**，不是"已知"

DOTA 不提供地理坐标、文件名无地理语义，同一机场/港口可能同时出现在官方 train 与 val。**我们既无法证明有泄漏，也无法证明没有**——报告用词必须是"**未排除**"，结论限定为"同分布留出"。

### 4.3 TTA

- **主表**：单尺度、滑窗 stride 1/3、**无 TTA**；
- **附表**：同模型 + d4 TTA，仅说明增益，不进主表。

### 4.4 同事配方复述（修正版）

`use_amp: False`、`scale_min/max 0.5/2.0`、`aux_weight 0.2`、1024 裁块、batch 12（6 卡）、200 epoch、滑窗 1/3 + d4 TTA。

### 4.5 数据溯源

iSAID/DOTA 未登记 `configs/downloads/catalog.yaml`，也无 sha256。建议补两条 catalog 记录并记校验和；路径统一写 `data_root/raw/isaid/...`。

## 5. 算力与 GPU 优先级

### 5.1 按迭代数的预算

| 项 | 数值 |
|---|---|
| 计划步数 | 25k 步 |
| 有效 batch | 8 |
| 总样本 | **20 万** |
| 若吞吐 1 张/秒 | **≈ 2.3 天 / 种子** |
| LIM 三种子 | ≈ 7 天 |
| 5 主干 × 3 种子 | **≈ 35 天**（单卡） |

以上吞吐**尚未实测**，仅用于说明量级。

### 5.2 范围建议：先 1 个种子 + 冻结轨

- 第一轮：**B2U、LIM、1 个种子**（exploratory，约 2–3 天）→ 拿到第一个可信数字与真实吞吐；
- 有效后：LIM 补到 3 种子；再逐个接新主干（每个主干先 1 种子，再补 3 种子）。

### 5.3 GPU 优先级（新增决策项）

当前占用：4090 在跑 T4 DEM 诊断（预计 2026-10-29 15:10 结束），3080 已预留给业务侧新项目。

**因此**：

1. P0-b 吞吐 smoke **不能与 T4 DEM 并行**，必须等 4090 空出（或排进 lane 队列）；
2. iSAID 与既有的 T1S/T8 补跑会抢同一张 4090，**需要明确谁先**（§9）；
3. 若 iSAID 排前面，T1S/T8 的收尾顺延。

## 6. home / away

- LIM 预训练于 **Million-AID（Google Earth 航拍，224）**；iSAID/DOTA 也大量来自 Google Earth → **LIM 主场**；
- 其余主干预训练以 10 m 级卫星为主 → **客场**；
- **Million-AID 与 DOTA 是否存在同区域重叠：未验证**，报告须写"未排除"；
- 结论不得把主场优势读作架构优势。

## 9. 决策项

已确定：

1. ✅ 不作选型依据，按"能力谱系 + home/away"表述；
2. ✅ 所有主干统一一个头；
3. ✅ 第一轮冻结主干（B2U）。

待确认：

4. 统一头采用**自研 torch-only UPerNet（GN）**、并采用 **registry 做法 B（不动 schema）**，可以吗？
