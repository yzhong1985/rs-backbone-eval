## 一、结论先行

**建议：沿用我们的框架（`rs-backbone-eval`），从同事框架里移植模型代码和数据接口。**

理由不是"我们的更好"，而是两者定位不同、正好互补：

| | 同事框架 `rs_segmentation` | 我们 `rs-backbone-eval` |
|---|---|---|
| 定位 | 单数据集训练脚本，目标是把一个模型在一个数据集上训到最好 | 多主干横向评测，目标是**不同模型之间可比、可追溯** |
| 结果记录 | 结果目录 + checkpoint | `run.json`（git commit、manifest sha256、权重 sha、显存、耗时）+ 审计 + supersede + 报告 + Portal |
| 数据 | 预切好的 crop 列表（路径写死） | manifest jsonl + sha256 + `audit-data`（波段/时相/组泄漏检查） |
| 轨道 | 只有全量微调 | B0/B1/B2/B2S/B3 分轨 |
| 并行 | DDP 6 卡 | 单卡 lane + 队列 |

**要交给上级的评测结论，必须是"同一协议下多个模型"的对比**——这件事只有我们的框架在做。同事框架里已有的模型代码（MiT-Huge）和 iSAID 数据接口（16 类、滑窗评测）可以直接搬过来，不必重写。

一句话：**代码复用他们的，协议与账本用我们的。**

### 2.3 LIM 权重核查

`/home/yzhong/models/mit_huge_600.pth`（6.2 GB）：

| 项 | 实际情况 |
|---|---|
| 结构 | `{model, optimizer, epoch, scaler, args}`，`model` 含 677 个张量 |
| 参数量 | **552 M** |
| 架构 | **MiT-Huge（SegFormer 编码器）+ MAE 式预训练 decoder** |
| 四级通道 | `patch_embed1..4` → **256 / 512 / 1024 / 2048** |

## 三、建议方案

### 3.1 分工

```
rs_segmentation（参考/移植）        rs-backbone-eval（落地）
├─ MiT-Huge 编码器        ──→      workers/lim/
├─ UperNetAlignHead       ──→      src/rs_backbone_eval/heads.py（共享）
├─ iSAID 数据接口         ──→      src/rs_backbone_eval/data/datasets/isaid.py
└─ 训练配方（参考）       ──→      configs/protocols/ + 任务 notes
```

### 3.2 关于"统一 UPerNet 头"——需要先明确一件事

**统一 UPerNet 会让现有分数不可直接比较**，因为目前所有 B1/B2 结果用的都是 `lite_spatial_head`。换头等于换了一条轨道，必须：

- 新开轨道（建议 `B1U` / `B2U`），**不并入现有 B1/B2**；
- 若要横向对比，现有主干需要在新轨道下**重跑**；
- 报告里禁止把"轻量头"和"UPerNet 头"的数字放在同一张排名表。

技术上有两种难度：

| 主干 | 金字塔来源 | 难度 |
|---|---|---|
| **LIM（MiT-Huge）** | 原生 4 级（H/4、H/8、H/16、H/32） | **最简单**，UPerNet 就是为这种结构设计的 |
| Prithvi | ViT token 序列抽层（我们 B0 已用 `[5,11,17,23]`） | 中，已有先例 |
| Clay | 8×8 patch token 抽层 + reshape | 中 |
| OlmoEarth | 稠密 token `[B,PH,PW,T,BS,D]`，需对时相做池化 | 中 |
| AnySat | token 展平顺序特殊，需逆向还原 | **最高**，有踩坑风险 |

必须在报告里写明：**对纯 ViT 主干，UPerNet 的金字塔是人为构造的近似，不是原生多尺度特征**。

### 3.3 iSAID 协议（建议，待拍板）

| 参数 | 建议值 | 理由 |
|---|---|---|
| 裁块 | 1024×1024，stride 512 | 与同事配方一致，便于对照 |
| 类别 | 16（15 类 + 背景），`ignore=255` | 官方定义 |
| 训练轮数 | 先 50，再视结果决定是否 200 | 与我们其他任务的预算口径接近 |
| 评测 | 滑窗 stride 1/3 + d4 TTA | iSAID 社区标准做法 |
| 报告口径 | **必须同时给出"无 TTA"的分数** | TTA 会显著抬分，防止被质疑 |

切块数量是本方案最大的不确定项：按 1024 裁块、stride 512 估算，单张图约 20–60 块，训练集总量在 **3 万–8 万块**量级。**必须先做数据体检（图像尺寸分布、类别分布、切块总数），再定最终协议**——这也是排期上的第一个 gate。

## 五、风险清单

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **许可限制**：iSAID/DOTA 仅限学术用途 | 若对外发布或进入产品材料，存在合规问题 | 已在业务侧确认为"评测用途"；建议写入报告与评审记录 |
| R2 | **LIM 只吃 3 通道 RGB** | 无法直接用于 T1/T2（6 波段），不能与 Prithvi/AnySat 在所有任务上横比 | 先在 iSAID（RGB）上评测；跨任务需要光谱适配器，属额外工作 |
| R3 | **UPerNet 在纯 ViT 上是近似** | 跨主干比较可能被质疑"头不统一" | 报告明确标注；只比较同一轨道内的结果 |
| R4 | **TTA 抬分** | 不同模型若 TTA 不一致，分数不可比 | 协议写死滑窗与 TTA；同时报告无 TTA 分数 |
| R5 | **掩码颜色映射未校验** | 若误用实例掩码，整批评测作废 | P0 先用官方 devkit 的 color map 校验（抽查 40 张仅 13 种颜色，需确认） |
| R6 | **算力** | 1024 裁块 + 552M 主干，单卡每种子 10–15 h；若走 200 epoch 则翻数倍 | 先 50 epoch；先 LIM 单模型，验证有效后再扩到其他主干 |
| R7 | **与同事结果不可直接合并** | 他们的配置是 200 epoch + 6 卡 + TTA，与我们的协议不同 | 报告单列，不与他们已有的 iSAID 分数拼表 |
