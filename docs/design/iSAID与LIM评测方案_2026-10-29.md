## 0. 与 2026-10-26 决定的关系（需求已澄清：不是路线调整，是口径需要写明）

`docs/reports/阶段进展更新_2026-10-26.md` 第 60 条记录：

> **不再安排 LIM 对照（2026-10-26 决定）。** 新底座的目标是 RGB 做不到的四波段/SAR 能力，与高分辨率 RGB 模型不在同一任务上竞争，**不以"超过 LIM"作为验收条件**。

**需求澄清（2026-10-29）**：上级要看的不是"新主干能不能赢 LIM"，而是"**在 LIM 的主场任务（iSAID，纯 RGB 高分辨率）上，这些新主干各自能做到什么水平**"。这与 10-26 的决定并不冲突——该决定排除的只是**把"超过 LIM"当作底座验收条件**，并没有禁止在共同任务上记录相对位置。

因此本方案按此口径执行，但必须把三件事写死，否则仍然会被误读：

1. 结论表述为"**在同协议下的能力谱系**"，不是"选型依据"；
2. 所有结果标 **home / away**（§6）——LIM 在 iSAID 上是主场，其他主干是客场；
3. 不出现"LIM 优于/劣于我们的基座"这类总结句；不因此调整 10-26 的选型路线。

### 两种交付范围（当前需求是 B，但 A 是它的前置）

| | **方案 A：只给 LIM 一个 iSAID 分数** | **方案 B：LIM + 新主干，同一 UPerNet 与协议（当前需求）** |
|---|---|---|
| 回答的问题 | LIM 在 iSAID 上做到多少 | **新主干在 LIM 的主场任务上各能做到什么水平**（LIM 作为主场参照） |
| 要做的事 | LIM worker + iSAID 管线 + 一个 UPerNet | A 的全部 + 4 个主干的四级金字塔适配 + 新轨道接线 + 基线重跑 |
| 开发量 | 约 **2–3 天** | 约 **5–6 天** |
| 算力 | 3 个种子（LIM） | 3 种子 × 5 个主干 |
| 结论能写 | "LIM 的 iSAID 成绩是 X，协议如下" | "在本协议与统一头下，新主干 A/B/C 的成绩为 …，LIM 为 …（主场参照）" |
| 结论**不能**写 | 任何跨模型比较 | "LIM 比我们的基座强/弱，所以应选/不选某个底座"（home/away 不对等，见 §6） |

**建议**：A 是 B 的天然前置——先把 LIM 的分数与协议跑通，再依次接入新主干（每接一个主干就能出一格结果，不必等全部接完）。这样吞吐与成本先用实测数据锁死，避免一次性承诺 5 个主干的算力。

### 1.3 LIM 权重（v1 有错，此处为复核结果）

| 项 | v1 写法 | **实际** |
|---|---|---|
| 参数量 | 552 M | **552.3 M 总量 = 编码器 524.4 M + 预训练 decoder 27.9 M**；`run.json` 应记 524.4 M + 下游头 |
| 预训练方法 | "MAE 式" | **MixMIM**：`args.model='mixmim_base'`、`mask_ratio=0.5` |
| 预训练数据 | 未提 | **Million-AID**，`input_size=224`（航拍 RGB） |
| 训练进度 | 未提 | **`epoch=150`，而 `args.epochs=300`** → 这是训练到一半的快照，不是最终权重 |
| 位置编码 | 未提 | 有 `absolute_pos_embed`，形状 `(1, 3136, 256)` = **56×56**（224/4）；换到 1024 输入是 256×256 = **65,536** 个位置，**必须插值并记录** |
| Mona/adapter 键 | 假设存在 | **一个都没有**；权重是纯 MiT 编码器 + MAE decoder |

**直接影响**：

1. 不能照搬同事的 `mit_mona_plus.py`——那份实现含 Mona 结构，参数对不上。应移植**不带 Mona 的 `mit.py`**；若要用 Mona，必须作为**单独声明的实验变量**，不能默认启用。
2. 同事 iSAID 配置里加载的是**另一份权重**（`mitmonaV3_H_stage4_600W/checkpoint499.pth`，epoch 499），与本份 `epoch=150` 不是同一个模型。**v1 的 R7 比原来写的更严重：连权重都不同。**

## 2. 「统一 UPerNet 头」到底用哪一个

### 2.1 三个候选

| 候选 | 现状 | 评价 |
|---|---|---|
| **terratorch `UPerNetDecoder`** | 我们仓库已在用（`workers/prithvi/src/prithvi_worker/t1_baseline.py`，B0 协议） | ✅ 标准 UPerNet，依赖已装，建议作为统一头 |
| 同事的 `UperNetAlignHead` | 在 `rs_segmentation` 里 | ❌ 实为 PPM+FPN+**AlignedModule**（SFNet 式），带 aux loss；与文献 UPerNet 不同名不同物 |
| 自写 | — | 不必要 |

**结论**：统一头建议直接用 terratorch 的 `UPerNetDecoder`；同事那个头只作为"另一种融合方式"的可选对照，不能叫 UPerNet。

### 2.2 BN 问题（必须写进协议）

同事配方用 **SyncBN + 6 卡 batch 12**（单卡等效 batch 2）。我们的口径是**有效 batch = 2**，BN 统计会明显退化。处理方式二选一，并在协议里声明：

- 用 **GroupNorm** 替换 BN（推荐，与 batch 无关）；
- 或**冻结 BN 统计**（`freeze_bn_stats=True`），沿用预训练/初始统计。

### 2.3 更正：现有轨道并非都用一个头

v1 写"所有 B1/B2 都用 `lite_spatial_head`"是错的。实际情况：

| 头 | 用在 |
|---|---|
| `lite_spatial_head` | T1 / T1S / T4 / T8 等单时相任务 |
| `temporal_segmentation_head` | **T3 / T5（多时相）** |
| `lite_spatial_head + spectral_adapter` | AnySat 侧输入适配 |
| `lite_spatial_head + band_adapter` | T8（GF-2 4 波段） |
| `upernet_decoder` | Prithvi B0 参考协议 |

因此"统一 UPerNet"不是把某个既定头换掉，而是**新增一条头 + 轨道**。

## 4. 协议设计（修正）

### 4.1 不能"验证集当测试"

框架在 **validation** 上选 checkpoint（`selection.py`），测试集只报一次。iSAID 只有官方 train/val，若把 val 当 test，就没有选模型的集合。

**做法**：从 **train 原图**中按组切出 10–15% 作为 validation（用仓库已有的 `holdout-manifest`，按 `group_id` 切分），**同一张原图切出的所有块必须落在同一个 split**。官方 val 作为 test，只评一次。

### 4.2 组泄漏

DOTA 不提供地理坐标，文件名（`P0000`…）也无地理语义；同一机场/港口很可能同时出现在官方 train 与 val 中。

**处理**：无法可靠分组 → **如实登记为已知泄漏**，结论限定为"同分布留出"；不得声称跨区域泛化。报告的"可主张范围"一节必须写明。

### 4.3 TTA 口径

不再声称"滑窗 + d4 TTA 是社区标准"（评审意见成立）。建议：

- **主表**：单尺度、滑窗 stride 1/3、**不加 TTA**；
- **附表**：同模型 + d4 TTA，仅用于说明增益。

### 4.4 同事配方复述修正

| 项 | v1 写法 | 实际配置 |
|---|---|---|
| 混合精度 | AMP | **`use_amp: False`** |
| 增强 | 未提 | `scale_min: 0.5`、`scale_max: 2.0` |
| 辅助损失 | 未提 | `aux_weight: 0.2` |
| 裁块 / batch / epoch | 1024 / 12 / 200 | 1024 / 12（6 卡） / 200 |
| 测试 | 滑窗 1/3 + d4 | `test_mode: slide`、`tta_mode: d4` |

### 4.5 数据溯源

- 该数据**不在** `configs/downloads/catalog.yaml` 中，也没有 sha256；
- 建议：补 catalog 条目（或至少把各 zip 的 sha256 与来源 URL 写入 `run.json` 的 dataset 段）；
- 文档中的路径统一写成 `data_root/raw/isaid/...`（实际 `data_root=/geodata/rs-eval/data`）。

## 5. 算力：v1 的数字是错的

### 5.1 错在哪

按 v1 自己的数字：3 万–8 万块 × 50 epoch = **150 万–400 万个 1024² 样本**。

要在 10–15 小时内跑完，需要 **约 28–110 张/秒**。而 524 M 参数的 MiT-Huge 在 1024² 输入下：

- 第一级 token 数 = (1024/4)² = **65,536**，是 224 输入的 16 倍；
- 同事的配方是 **6 卡、每卡 1024² 下 batch 2、且关闭 AMP** 并开梯度检查点——说明单卡已经吃满；
- 现实吞吐更可能是 **1 张/秒量级**，即每种子 **17–46 天**。

v1 写"每种子 10–15 小时、三种子 1.5 天"是**错了一到两个数量级**，本版撤回。

### 5.2 P0 必须先做吞吐 smoke（新 gate）

在写任何排期承诺之前，先跑固定 `200 iter` 的测量，输出：

| 指标 | 用途 |
|---|---|
| 图像/秒（512² 与 1024² 各一组） | 决定裁块大小 |
| 峰值显存（开/关梯度检查点） | 决定 batch 与是否可上 3080 |
| `absolute_pos_embed` 插值后是否正常收敛（前 20 iter loss 下降） | 排除位置编码错位 |
| 单次验证（滑窗 1/3）耗时 | 估算评测成本 |

**没有这组数字，不承诺任何小时数**。

### 5.3 预算改为按迭代数

建议不再用 epoch 作为主预算，改为**固定优化步数**（例如 20k–30k 步，有效 batch 8），并对训练块做**按 epoch 抽样**（例如每 epoch 采 8000 块）。这样成本与切块总数解耦，也避免"块多就自动训更久"的隐性不公平。

## 6. home / away（新增，必须写进报告）

- **LIM 的预训练数据是 Million-AID（Google Earth 航拍，224 输入）**；
- **iSAID / DOTA 的图像同样大量来自 Google Earth**；
- 因此在这组对比里 **LIM 是主场，Prithvi / AnySat / Clay / Olmo 是客场**（它们的预训练以卫星 10 m 级为主）。

报告必须：

1. 按 T8 的做法标注 **home / away**；
2. 说明 **Million-AID 与 DOTA 是否可能包含同一区域**——本版**未做**这个比对（需要抽样影像匹配），在结论里应写明"未排除"；
3. 明确"LIM 在 iSAID 上的优势**不能**外推为业务选型依据"。
