# 评测框架复审：3b4460a

日期：2026-10-14。审查版本：`3b4460a`，已从远端 main 快进同步。本轮新增范围为 `bbeb5c4..3b4460a` 的九个提交，同时核对先前审查提到的相关现有路径。

依据：[项目审查](./项目审查_2026-10-14.md)、[评价体系改进建议](./遥感Backbone评价体系改进建议.md)。本轮没有修改训练或汇总代码；本文件是新增复审记录。未运行 GPU 训练，未取得外置数据、上游实际 checkout、历史 checkpoint/run，不能据此认定历史成绩全部受到同一问题影响。

结论：这次修改确实落实了多个建议，公共统计与数据工具更完整；但若立即开始完整的随机初始化、少标注或地理泛化实验，仍可能产生错误缓存、实验混合和选模偏差。建议先完成下述 P1 验收，再投入大规模正式重跑。新增工具的单元测试通过，不等于所有 worker 已接入对应功能。

## 1. 最需要先修的发现

### R1／P1：实验分组仍会混合初始化、标注预算和数据版本

位置：`src/rs_backbone_eval/matrix.py:54`、`:133`、`:141`；`report.py:108`、`:139`。

`variant_key()` 仍只有 head、preprocessing、LR、encoder 输入尺寸，没有 `init`、`label_fraction`、manifest、checkpoint、训练预算、裁剪和代码/配置版本。新增 `RS_EVAL_INIT` 和标注比例 tags 没有参与分组。随后 `canonical_runs()` 只按 seed 保留最新运行，因此不同实验条件会被误当作重试。

复现：同一模型/任务/协议，seed=42，预训练/100% 标注成绩 0.8，之后随机初始化/10% 标注成绩 0.2；汇总只剩后一条，`variants=1`、均值 0.2。不同 seed 混在一起时，也会变成混合条件的均值与标准差。

修复：建立完整、明确的实验配置身份，区分搜索候选与比较条件；在同一实验配置内才进行 seed 去重。报告、Portal、D2、少标注表应共用筛选结果。不能只把 init 加入 variant 后再从所有 init 中挑一条 headline；不同初始化、标注预算和输入信息应保持可见的独立 panel。

验收：改变初始化、标注比例、manifest、checkpoint、crop 或预算后不会覆盖其他条件；真正同配置重试不会增加种子数；报告与 Portal 的原始 run 来源一致。

### R2／P1：Clay T3/T5 特征缓存会串用预训练与随机初始化

位置：`workers/clay/src/clay_worker/t5.py:309`、`:317`、`:325`；`t3.py:157`。

新缓存工具确实把 manifest 内容加入 key，但调用处没有绑定实际 encoder 权重、初始化方式、随机初始化 seed、预处理参数、光谱/GSD 以及代码版本。预训练模型与随机模型共享相同 key；不同随机 seed 的 encoder 也可能复用同一特征。随机初始化对照因此可能实际训练在预训练特征上。

另外，仍以 `path.is_file()` 判定缓存完成，并直接在目标文件创建 memmap。中断留下的部分文件可以继续复用，未核对 shape/dtype/完整样本数。

复现：提取当前源码的真实 `_feature_cache()` 函数，对已有文件执行快速复用分支。切换 `RS_EVAL_INIT=pretrained/random` 两次返回相同文件；文件实际 shape 为 `(1,)`，函数仍返回预期 `(1,3,1024,28,28)`。此复现没有执行或伪造 GPU 特征提取，只验证真实的缓存选择与验收分支。

修复：key 纳入实际权重身份与完整前处理身份；随机初始化至少绑定 seed 与确定的初始化实现，严谨时记录初始 state hash。特征缓存写临时文件，确认 cursor/shape/dtype 后原子提交并保存元数据。新缓存版本不得继续采用缺少身份的旧缓存。

验收：权重、init、随机 seed、波段或归一化变化使 key 变化；相同冻结 encoder 可跨头部 seed/LR 复用；不完整或 shape 不符文件被拒绝。

### R3／P1：T1 的实际验证指标没有驱动超参选择

位置：`matrix.py:78`、`:109`；实际 T1 写入见 `workers/anysat/src/anysat_worker/t1_adapter.py:355`、`workers/prithvi/src/prithvi_worker/t1_finetune.py:217` 附近。

`mean_validation()` 仅读取 `validation_mean_iou`。T1 worker 写的是 `validation_water_iou`，B0 写的是验证 loss；后续 F1/RMSE 也未建立通用选择定义。T1 候选获得同一个负无穷分数，同 seed 数下仍会受输入顺序影响。`_rank()` 也只按分数越高越好，不适用于验证 loss/RMSE。

复现：两个 T1 候选真实 validation water IoU 分别为 0.5/0.9，LR 分别为 1e-4/3e-4。低分候选先输入会选 1e-4；调换顺序则选 3e-4。已有测试使用的 `validation_mean_iou` 路径能通过，却未覆盖真实 T1 tags。

修复：统一记录选择指标名称、方向、split 和数值，并明确 `selected_config_id`、search/final phase。缺失选择证据时不要自动宣称“验证集最优”。锁定配置后跑正式种子，不将每次重新生成报告理解成一次合法超参选择。

验收：water IoU/F1 最大化、loss/RMSE 最小化都选正确配置；输入顺序不影响结果；同验证分按预先固定规则处理。

### R4／P1：少标注报告再次直接平均了重复与异构运行

位置：`report.py:371`、`:381`。

少标注表按 task/track/model/比例收集所有具有主指标的 run，直接平均。没有 completed 筛选、配置选择、seed 去重或 init/manifest/头/输入隔离。即使主矩阵已去重，这张新表也会重新计入同 seed 重试；有中途主指标的 failed/running 记录也可能进入。

复现：同条件 seed=42 两次成绩 0.8 和 0.6，表中直接显示 0.7000。主矩阵的一 seed 一结果规则没有复用到这里。

同时，比例是手动环境 tag，不是由派生 manifest 自动证明。CLI 不会自动携带抽样单位、父 manifest、抽样 seed、实际标注组数；只写 `RS_EVAL_LABEL_FRACTION=0.1` 不会把数据变成 10%。这并非环境变量功能本身错误，但需要防止标签与数据失配。

修复：从已锁定配置的 canonical completed runs 生成曲线，展示 n、均值/标准差与实际标注量；派生 manifest 保存父清单、unit、sampling seed、原始/保留数量等元数据。不同抽样 seed 的波动与训练 seed 波动分开报告。

验收：重复、失败、其他 LR/init 不污染曲线；比例与实际数据一致；10%/30%/100% 使用同一排序形成嵌套子集，固定验证测试。

### R5／P1：新 holdout 工具不保证地理隔离，也尚不能完整执行评价

位置：`data/subset.py:78`、`:90`；`cli.py:261`；`configs/tasks/T1_flood.yaml`、`T1_flood_sar.yaml`、`T8_gf2_landcover.yaml`。

工具只移动 source_split 中被选组的行。如果同一 group 在原 validation/test 中也有样本，那些行仍留在旧 split。T2/T5 现有构建器会把训练 chips 划成项目 train/validation，而 group 使用地区/tile，因此这类跨组场景需要实际排查；本轮不能断言外置 manifest 的具体泄漏数量。

复现：同一 group 各有 train/validation/test 一条，调用 holdout 后同一 group 出现在 geographic_holdout/validation/test。工具没有拒绝这类输入，也没有重新规划该地区全部观测。

其他缺口：

- registry 的默认 allowed_splits 增加了新名称，但 T1/T1S/T8 显式列表仍不允许 `geographic_holdout`，严格 probe 会拒绝相应清单。
- worker 的评价 split 仍按 test/official_validation 等固定值，没有读取新增 holdout 进行评价的完整路径。存在 holdout 行不等于已报告 holdout 成绩。
- `holdout-manifest --split temporal_holdout` 仍执行随机 group 选择，并未按年份或采集时间划分，不能称跨年泛化。

修复：地理 holdout 先确定真正地区/事件分组；对原 split 跨组明确拒绝或在新的协议版本中整体隔离，保持官方 benchmark 与新地域测试并存。时间 holdout 单独实现日期截止及观测可用性规则。CLI、TaskSpec、worker、报告联通，禁止只改 split 名字。

验收：holdout 地区不参与训练和验证选模；日期不能跨年窗口泄漏；使用实际 T1/T5 清单能够 dispatch、评价并展示独立结果。

### R6／P1：完整标签监督只修了 T5 的两条路径，其他相同问题仍在

已修：Clay T5 缓存训练与 Prithvi T5 冻结训练，均上采样 logits 到完整 224 网格再算损失。

未修位置：Prithvi `t1_frozen.py:227`、`t2.py:230`、`t3.py:219`；Clay `t3.py:141`、`:314`。这些冻结路径仍对标签作最近邻下采样后算 loss。Clay T3 的验证选模也基于粗网格标签，而最终评价是完整网格。

影响：不同模型可见的有效监督像素、细小目标和边界不同；相同轻量头不能抵消差异。建议将 logits 对齐原始有效标签网格作为公共损失路径，并对所有冻结/缓存分支做遍历验收。

验收：同一标签 valid-mask 集合参与各模型损失；一个仅在细网格出现的小目标不会因为选择骨干而失去监督；验证选模与最终评价的空间口径一致。

## 2. 统计与报告的其他问题

### R7／P2：D2 分类与聚合会混入非扰动 split 和不同训练轨道

位置：`matrix.py:232`、`:261`。

任何“与 primary 同名、非 primary、不同 split”的指标都被视为扰动，validation/普通 holdout 也会进入该列表。复现中 test=0.8、validation=0.6 被解释成“扰动下降 0.2”。不同 split 的自然难度差不能解释为同模型同样本输入扰动效应。

`_d2_by_model()` 又只按 model/task/perturbation 聚合，丢失 B1/B2、配置和 init，且不 canonical 去重。建议显式标注 evaluation kind、baseline split、扰动身份及样本支持集；holdout 泛化与输入扰动分别汇总，使用与主矩阵一致的配置/种子过滤。

### R8／P2：D1 和 Pareto 仍比较不同覆盖集合，失败率也混合动作

位置：`matrix.py:285`、`:338`、`:365`。

D1 每个模型只平均自身完成任务，没有限制到共同任务或预先规定集合；耗时也平均各自任务，然后直接比较 Pareto。复现中只做 T1 的模型和做 T1/T2 的模型仍生成同一 Pareto 标记。显示 coverage 不足以让这种比较成立。

建议先逐任务做精度—成本 Pareto；跨任务汇总只使用同硬件、同预算、共同任务集并固定权重。缺任务暂不生成排名，保留原始结果。比例归一化对零误差、负 R² 等还需要适用性判断。

失败统计目前将 probe、train、运行中和其他实验混在 `failed/total` 里，不是定义明确的训练失败率；需限定动作/阶段、终止状态和配置。不同任务指标的标准差也不宜机械平均为整体稳定性。适配增益仍放在 D3，RMSE 的差值方向也未统一，宜转为 D1 的受控效果分析。

### R9／P2：输入兼容矩阵把“完成前向 probe”当作原生能力证据

位置：`matrix.py:405`、`:441`。

只要 record completed 且没有 adapter_parameters，就标 native，不要求任务评价指标；真实 probe 也会 completed。这样与函数说明“不把前向当已验证支持”不一致。failed run 有 adapter tag 也可能被标为 adapter，而不是待验证。

建议把输入接收方式（native/adapter/unsupported）与验证状态（仅前向/已训练并评价/失败/未知）分开；关联实际配置、任务成绩和成本，避免由缺失 adapter tag 推断原生支持。

### R10／P2：manifest 的记录仍来自文件名，和新 CLI 不兼容

位置：AnySat `runner.py:379`、Clay `runner.py:365`、Prithvi `runner.py:236`。

新 CLI 可把派生清单写成任意 out 名字，`RS_EVAL_MANIFEST` 也允许显式文件；但三家 RunWriter 接收到的 manifest_sha256 仍是文件名去掉扩展名。复现中 `fewshot.jsonl` 被记录为 `fewshot`，真实内容 hash 为 64 位另一个值。

建议统一在入口计算实际内容 SHA-256，或由调度器计算后传递并核对；固定清单时同时做 task-aware audit。数据追溯不能再依赖恰好以内容 hash 命名。

### R11／P2：随机初始化入口的记录与实际权重尚未全部一致

已见 AnySat 相关训练入口、Clay 多任务和 Prithvi 自定义任务按环境变量跳过预训练；Prithvi T3 复用 T5 build_encoder，因此也覆盖，不应仅因本文件没有 random_init import 判漏。

但 Prithvi B0 `t1_baseline.py:178` 仍固定 `pretrained=True` 和 checkpoint，RunWriter 却无条件记录 init 环境 tag。设置 random 后，B0 可以被标记 random 但实际仍加载预训练。所有 train runner 也仍要求并记录预训练 checkpoint，即使随机分支没有使用。

建议统一初始化解析，未知值报错；不支持随机控制的轨道明确拒绝，B0 若继续保持参考复现就不允许该覆盖。记录实际加载状态和初始权重身份，而不是只记录请求值。随机对照不是任何轨道加一个 tag 就完成。

## 4. 建议下一轮执行顺序

1. 先修 R1/R2：完成实验身份与缓存身份。否则新增消融可能直接产生无效数据。
2. 修 R3/R4：统一验证指标选择和 canonical 筛选；先用合成 RunRecord 验证主表、D2、少标注表不混条件。
3. 修 R5/R10：将派生数据协议接通 TaskSpec/worker/报告，核查地域与时间隔离及真实 hash。
4. 统一剩余 loss grid，恢复 Clay 缓存时序信息；加入实际 worker 的小模型替身测试或上游单批次验收，覆盖冻结/微调/adapter/缓存路径。
5. worker 输出 group confusion、选中 checkpoint、实际 optimizer steps 和一致 phase 成本，报告计算配对 CI。Prithvi T5 在 frozen 分支设置 train_started 后未写 phases[train]，先补此项。
6. 最后锁定 T1/T2 共同协议，按相同搜索预算和三 seed 重跑；T5 同头逐帧与原生时间融合分 panel。历史不一致结果保留版本说明，不覆盖为修订协议的正式证据。

无需为了实现全面一次扩到所有任务；优先让 T1 和一个多时相任务完整走通“数据身份→训练语义→最佳权重→分组指标→统一报告”。
