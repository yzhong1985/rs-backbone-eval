## 2. 来源与校验

官方只提供百度网盘与 Google Drive。本机到 Google Drive 只能走 SOCKS5 代理
（`127.0.0.1:1080`），实测**极慢**：一个 302 要 11 s，12 s 内 0 字节，按此速度 15 GB
不可行。因此改用 **hf-mirror 上的转存**（`125oii/whu_opt_sar`，卡片标注上游即官方仓库），
实测 **75 MB/s**，3.5 分钟下完。

| 文件 | 大小（字节） | sha256 |
|---|---:|---|
| `optical.zip` | 10542351536 | `a1a5dcfff2ec7274ba0576c99bfe60f491aa2bf2ecd34325f212ec21f8a35bd9` |
| `sar.zip` | 4332069920 | `5c71d6ca7d50bbbc2f0ca12b475115c07395e17a55388015993dd57d93b7047d` |
| `lbl.zip` | 203121910 | `f9b3b281f490f9442b28ce28c1d209ad4448b6cb8c9cb83fa9dc8304d03464c1` |

注意：

- 每个压缩包内有 **200 个 tif = 100 幅 + 每幅一个 `(1)` 副本**（Google Drive 同步产物）。
  `scripts/fetch_whu_opt_sar.sh` 只解出非副本成员，得到 100 幅/模态。
- sha256 标识的是**这份镜像拷贝**，不是官方归档；`optical.zip` 的 sha 与 HF LFS 的
  `oid` 一致，可交叉核对。
- 未放进 `configs/downloads/catalog.yaml`：该目录的 `target_dir` 若解析到数据根之外
  （本部署就是用软链把大文件放根盘），Portal 的状态会显示 `invalid_target`。这类
  "账本外大文件 + 软链"的数据集与 AEF/OlmoEarth 一样，用脚本 + 本文档登记。

校验结果（2026-11-16）：

- 三个模态各 **100/100** 个文件名与官方 `The division of the dataset.txt` 完全一致，
  无缺、无多余；
- 全部为 `5556 × 3704`、`crs=None`、单位变换；
- 标签值域实测 `{0,10,20,30,40,50,60,70}`，非背景占比 99.999%。

## 3. 地理参考：文件名就是 GB/T 13989-2012 图幅号

影像本身**没有**投影、仿射、GCP 或 RPC（`rasterio` 打开得到单位矩阵），作者在
[issue #10](https://github.com/AmberHen/WHU-OPT-SAR-dataset/issues/10) 也说明不提供带
坐标的影像。但文件名是 1:50,000 国家基本比例尺地形图分幅号：

```
N H 49 E 004 021 .tif
│ │  │  │  │   │
│ │  │  │  │   └ 1:50k 列号，001 = 最西，24 列 × 15′
│ │  │  │  └──── 1:50k 行号，001 = 最北，24 行 × 10′
│ │  │  └─────── 比例尺字母，E = 1:50,000
│ │  └────────── 1:1,000,000 图幅列号，自 180°W 起算（49 = 108–114°E）
│ └───────────── 1:1,000,000 图幅行字母，A = 0–4°N，H = 28–32°N
└─────────────── 北半球
```

- 纬度：`lat_n = (行字母序号) × 4° − (行号 − 1) × (4°/24)`
- 经度：`lon_w = (列号 − 1) × 6° − 180° + (列号 − 1) × (6°/24)`

**关键自洽性检查**：`0.25° / 5556 = 0.1666667° / 3704 = 4.49964e-5 °/px`，经、纬两轴
完全相等。如果是 5 m 投影网格，两轴的"度/像素"不可能相等，所以栅格确实是按图幅经纬度
铺满的。这与"文件名定位"互相印证。

解码工具：

```bash
uv run python scripts/whu_tile_bbox.py NH49E004021
# NH49E004021: lat 31.3333..31.5000, lon 113.0000..113.2500
# pixel grid 4.49964003e-05 deg/px (x) x 4.49964003e-05 deg/px (y)
# affine a,b,c,d,e,f = (4.49964e-05, 0.0, 113.0, 0.0, -4.49964e-05, 31.5)

uv run python scripts/whu_tile_bbox.py --check "The division of the dataset.txt"
# 100 names, 100 unique sheets
# lat 29.3333..32.6667  lon 109.5000..116.0000
```

## 4. 三处必须注意的细节

1. **"5 m"只在纬向成立**：30.5°N 处 15′ 经度只有约 24.0 km，所以像元约
   **4.32 m（东西）× 5.01 m（南北）**。README 的 51,448 km² 是未乘 `cos(lat)` 的粗算，
   100 幅真实面积约 **4.43 万 km²**。按米做 buffer / 重采样时不能用 5 m 当两轴分辨率。
2. **图幅号定义在 CGCS2000 高斯投影**，直接按经纬度矩形近似会有几十米级偏差
   （子午线收敛、尺度因子）。对 10 m 的 AEF 特征够用；像素级配准要重投影到
   UTM 49N/50N，并按图幅选带（≥114°E 落在 50 带）。
3. **图幅级划分 ≠ 空间独立**：24×24 网格里相邻图幅共享边界，仍有空间自相关；
   报告里应写"图幅级空间隔离"，不要写"空间独立"。

## 5. 与 AEF 对齐的前提

- 本机的 AEF 只有**法国/PASTIS 那一块**：`data-aef/aef-cogs/2019` 共 17 个 8192² COG、
  45 GB，CRS 全是 `EPSG:32630`。**湖北没有覆盖**。
- 要用 AEF 当教师，需要另外拉 AEF 亚洲块：索引查询结果是 **2019 年 54 块**，整块约
  190 GB；按图幅窗口裁剪后约 **28 GB**。2026-11-16 已下 1 块做对齐验证（见 §7）。
- 或按既有路线：不读教师，只做"光学 / SAR / 融合"三种输入之间的学生对比（T1S 的
  SAR 轨已经是这种形态）。

## 6. 建议的对齐验证（不需要真坐标）

1. 取 2–3 幅，用解码 bbox 叠 **JRC Global Surface Water** 或 **ESA WorldCover**，
   看水体/建成区形状是否吻合；
2. 更有说服力：把 bbox 人为平移 ±0.05°/±0.1°，比较 AEF 特征与影像地物的相关性——
   正确位置应显著高于平移后；
3. 检查相邻图幅拼接处（如 `NH49E004021` 与 `NH49E004022` 的东/西边界）地物是否连续。

## 7. AEF 对齐验证（2026-11-16 已做）

### 7.1 AEF 覆盖

用官方索引 `derived/aef/aef_index.parquet`（302,466 行）查湖北包络
（109.5–116.0°E, 29.33–32.67°N）：

| 项 | 值 |
|---|---|
| 2019 年相交的 AEF 块 | **54 块**（UTM 49N 与 50N 两个带） |
| 单块大小 | 约 **3.5 GB**（8192×8192×64，int8 COG） |
| 全部拉取 | 约 **190 GB**（根盘 918 GB 可用，可行但重） |

本机现有 `data-aef/aef-cogs/2019` 只有法国 `EPSG:32630` 的 17 块，**不含湖北**，所以这次
单独下了一块做验证：
`gs://alphaearth_foundations/satellite_embedding/v1/annual/2019/49N/x59krd3qv03uem4vj-…tiff`
（3.56 GB，bounds 112.718–113.596°E / 31.074–31.827°N，实测 24 MB/s，2.5 分钟）。

### 7.2 验证方法（不依赖真坐标）

如果文件名解码正确，那么**用解码 bbox 采样的 AEF 特征应该能预测该幅的 WHU 标签**；
把采样窗口平移几公里后应显著变差。

- 特征：AEF 2019 的 64 维，按 WHU 像元中心（每 20 px 取一点，约 5 万点）最近邻采样；
- 标签：同一像素的 WHU 类别（去掉背景 0）；
- 分类器：逻辑回归（`class_weight=balanced`），**训练用该幅西半、测试用东半**（空间切分，
  避免同像元自相关）；
- 控制：把采样窗口平移 ±0.05°/±0.10°/±0.25°。

### 7.3 结果（两幅，macro-F1 为主指标）

| 偏移 | NH49E004021 acc / macroF1 | NH49E006022 acc / macroF1 |
|---|---|---|
| **正确（解码 bbox）** | **0.710 / 0.350** | **0.653 / 0.362** |
| +0.05° lon（≈5 km） | 0.219 / 0.097 | 0.098 / 0.071 |
| +0.10° lon | 0.222 / 0.097 | 0.119 / 0.074 |
| −0.10° lon | 0.212 / 0.095 | 0.160 / 0.080 |
| +0.10° lat | 0.219 / 0.097 | 0.068 / 0.057 |
| −0.10° lat | 0.331 / 0.113 | 该幅越界 |
| +0.25° lon | 0.306 / 0.107 | 该幅越界 |
| 多数类基线（acc） | 0.721 | 0.673 |

**结论**：正确 bbox 的 macro-F1 是 0.35～0.36，任何平移都掉到 0.06～0.11（**约 4 倍差距**，
两幅一致）。这同时验证了两件事：

1. **文件名解码是对的**——若解码错了，"正确"窗口不可能系统性优于所有平移；
2. **AEF 2019 覆盖湖北且确实携带与土地用途相关的信息**，可以作教师。

注意两个边界：① macro-F1 0.35 只是"粗探针"水平（64 维 int8、7 类、两幅），不代表最终精度；
② 平移实验测的是"对齐是否有意义"，不是像元级配准精度；像元级仍需按 CGCS2000 高斯投影
重投影后再比。

### 7.4 采样注意事项

- 该 AEF 块的仿射是 **南向上**（`e=+10`，`f=3,440,640`，bounds 的 bottom > top），按
  "北向上"读会得到上下翻转的结果；用 `~transform` 反算行号即可，或先检查 `transform.e` 符号。
- 一块 AEF（82 km）覆盖约 3×5 幅 WHU 图幅；建议**按图幅窗口裁剪**而不是保留整块：
  每幅 2400×1855×64 int8 ≈ **285 MB**，100 幅约 **28 GB**，比整块拉取的 190 GB 省一个量级。
