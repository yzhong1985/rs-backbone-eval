# AnySat T4 训练提速试验指南

日期：2026-10-24。代码核对基于 `510f117`，对应 `workers/anysat/src/anysat_worker/t4.py`。本文是试验步骤与实现建议，没有修改训练代码，也没有测得加速倍数。

用户提供的现象：3080 上 seed 17 约 35 min/epoch，18/50 轮，训练集约 2400 chips。按这个速度，50 轮约 29.2 小时/种子；实际总时间还受验证、检查点、最终测试和排队影响。下面先区分训练计算、读取、验证和保存开销，再决定是否调整后续两个种子的安排。

## 1. 先确认这次在跑什么

以正在运行的 `run.json` 和代码版本为准，不用队列名称推断轨道：

- `protocol_id`、`tags.backbone_frozen`：B1 全量微调，还是 B2 冻结骨干＋可训练 adapter。
- `tags.micro_batch`、`tags.grad_accum`、`tags.effective_batch`：确认实际批量与累积次数。
- `tags.encoder_input_px`、`tags.patch_size_m`：本版 T4 是 224 输入、160m patch 参数。
- `tags.learning_rate`、`tags.epochs_budget`、`git_commit`；验证频率和精度还需结合该版本源码、启动环境核对。

本版实现的关键点：

1. **冻结骨干不等于只计算小头。** B2 的光谱 adapter 仍可训练；为了计算 adapter 的梯度，计算图必须穿过 AnySat 骨干。代码在这种情况下明确使用 `torch.enable_grad()`。adapter 参数少，不代表反传便宜。
2. **训练已经使用 BF16 autocast。** 不要把“开启训练混合精度”重复算作新增提速方案。
3. **验证尚未使用 autocast，且每个样本调用 `torch.cuda.empty_cache()`。** 这是值得测量的优化点，但不能据此断言它占了每轮的大部分时间。
4. 每次读取样本都会打开影像/标签 HDF5，并把 128×128 缩放到 224×224。
5. 本版默认每 5 轮验证一次，每轮保存训练检查点。35 分钟是否包含这些工作，需要从时间记录确认。

本次能读取的是 89 机器的账本，没有拿到用户所述 3080 运行的完整时间记录，因此以上是代码事实，不是该进程的 profiling 结果。

## 2. 哪些现在能试，哪些需要实现

| 项目 | 本版状态 | 怎么试 | 是否改变实验条件 |
|---|---|---|---|
| DataLoader worker 数 | 有 `ANYSAT_WORKER_NUM_WORKERS` | 对照 4/8 等设置，CPU 核数不足时不盲目增加 | 不改变标签、模型和训练预算；需保持数据读取可复现 |
| micro-batch × accumulation | 已实现 | 快卡上对照 1×2 与 2×1 | 有效 batch 相同也不保证逐位相同，记录两项参数 |
| 缓存读取与 resize 后的输入 | **未实现专用开关** | 修改 Dataset 或增加磁盘缓存 | 可保持输入数值完全相同 |
| persistent workers / pinned memory | **T4 当前未配置** | 修改 DataLoader 和搬运逻辑 | 主要是工程优化 |
| 移除验证循环逐样本 empty_cache | **需改代码** | 对照验证耗时和峰值显存 | 不主动改变数值精度或选模频率 |
| BF16 验证 | **需改代码** | 对照完整验证集的 FP32/BF16 输出与选模结果 | 改变数值路径，需校验并记录 |
| FlashAttention | 构建时写死 `flash_attn=False` | 检查依赖兼容后改构造参数并短测 | 算子路径变更，需数值/梯度校验 |
| T4 两阶段冻结＋特征缓存 | **未实现**；已有 T5 路径可参考 | 新增 T4 B2S 流程 | 改变训练协议，必须单独报告 |

不要直接设置假想的 `ANYSAT_T4_CACHE=1`、`ANYSAT_FLASH_ATTN=1` 等变量：本版没有读取这些开关。修改前先搜索当前版本，避免环境变量看似设置成功、实际没有效果。

## 3. 先跑一个隔离的测速基线

在有空闲 GPU 的机器上执行，不与当前正式运行争抢同一张卡。下面是在项目根目录的 Bash 命令；`.env` 中的数据、权重、AnySat 源码路径应已可用。临时目录需要有检查点空间，模型与最佳权重可能占数 GB，可将 `/tmp` 改到空闲磁盘。

这组示例按 **B2 frozen_adapter、micro=1、accum=2、lr=0.001** 编写。先核对自己的正式配置；若当前任务是 B1 或采用其他参数，基线也要相应调整。

以下几段在同一个 Bash shell 中执行。基线只有两轮、每轮最多 50 个 optimizer steps；验证/测试各截取 16 个样本，仅用于测速，不能报告为任务精度。

```bash
set -euo pipefail
set -a
source .env
set +a

bench_dir=$(mktemp -d /tmp/anysat-t4-speed.XXXXXX)
export RS_EVAL_RUNS_ROOT="$bench_dir/runs"
export RS_EVAL_CHECKPOINT_ROOT="$bench_dir/checkpoints"
export RS_EVAL_CACHE_ROOT="$bench_dir/cache"
export RS_EVAL_CHECKPOINT_EVERY=1
export RS_EVAL_INIT=pretrained
export RS_EVAL_LABEL_FRACTION=1.0

export ANYSAT_WORKER_DEVICE=cuda
export ANYSAT_WORKER_EPOCHS=2
export ANYSAT_WORKER_LIMIT_BATCHES=50
export ANYSAT_WORKER_EVAL_LIMIT=16
export ANYSAT_WORKER_BATCH_SIZE=1
export ANYSAT_WORKER_GRAD_ACCUM=2
export ANYSAT_WORKER_LR=0.001
export ANYSAT_WORKER_NUM_WORKERS=4
export RS_EVAL_VAL_EVERY=1

printf '测速目录：%s\n' "$bench_dir"
git rev-parse HEAD > "$bench_dir/commit.txt"
nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv \
  > "$bench_dir/gpu.csv"

run_speed_case() {
    local speed_case="$1"
    /usr/bin/time -f 'ELAPSED_SECONDS=%e' \
      uv run rs-eval dispatch --action train --task T4 --model anysat_base \
      --protocol frozen_adapter --seed 17 \
      --run-id "anysat-T4-speed-${speed_case}" \
      > "$bench_dir/${speed_case}.log" 2>&1
}

run_speed_case baseline
tail -n 15 "$bench_dir/baseline.log"
```

每个新 case 使用不同名字，避免覆盖记录或检查点。重复基线可用 `baseline-repeat`。不同硬件执行同一组步骤，记录相同的数据清单哈希、权重版本、上游 AnySat 版本和依赖版本。

### 不改训练代码即可试的两个对照

```bash
# 仅改变读取进程数；这个子 shell 退出后设置自动恢复。
(
    export ANYSAT_WORKER_NUM_WORKERS=8
    run_speed_case workers8
)

# 仅在显存允许时测试；有效 batch 仍是 2。
(
    export ANYSAT_WORKER_BATCH_SIZE=2
    export ANYSAT_WORKER_GRAD_ACCUM=1
    run_speed_case batch2-acc1
)
```

50 个 optimizer steps 不等于 50 张图：1×2 和 2×1 两种设置每轮约处理 100 张图，数据量可比；验证 batch 仍由当前代码固定为 1。OOM 的 case 记录为不适用，不通过截取更少图片来伪装提速。

读取这批测速记录的汇总：

```bash
uv run python - "$bench_dir" <<'PY'
import json
import sys
from pathlib import Path

root = Path(sys.argv[1])
for path in sorted((root / "runs").glob("*/run.json")):
    record = json.loads(path.read_text())
    training = record["training"]
    print(json.dumps({
        "run": record["run_id"],
        "status": record["status"],
        "epochs": training.get("epochs_completed"),
        "optimizer_steps": training.get("optimizer_steps"),
        "wall_seconds": training.get("wall_time_seconds"),
        "peak_mb": training.get("peak_gpu_memory_mb"),
        "micro_batch": record.get("tags", {}).get("micro_batch"),
        "grad_accum": record.get("tags", {}).get("grad_accum"),
        "notes": record.get("notes"),
    }, ensure_ascii=False))
PY
```

`ELAPSED_SECONDS` 包含进程启动、模型加载、训练、验证、保存和最后测试；`training.wall_time_seconds` 的计时范围也不是纯 GPU 计算。两者都可比较同设置下的短跑，但**不能直接乘以数据集大小推算完整 epoch**。smoke 的验证频率和样本数与正式任务不同，启动与首次 kernel 开销占比也更高。

## 4. 怎样测出真正的耗时来源

需要在独立试验版本中增加阶段计时，或对几十个 step 使用 `torch.profiler`。至少分开记录：

| 项目 | 记录方法 | 解读 |
|---|---|---|
| 等待下一批数据 | 对显式 DataLoader iterator 的 next() 计时 | 等待明显时优先处理 HDF5、resize、worker 和缓存 |
| Host→GPU | CUDA event，配合 pinned memory 的对照 | 检查搬运与计算是否能重叠 |
| 前向＋loss | CUDA event | 区分骨干与头的前向更好 |
| 反向＋optimizer | CUDA event，记录累积窗口边界 | B2 仍有穿过骨干的输入梯度计算 |
| 一次完整验证 | 入口/出口同步 GPU 后用 wall clock | 单独比较 FP32、BF16、empty_cache 的影响 |
| 一次 checkpoint 保存 | 保存入口/出口 wall clock | 留意 GPU→CPU 拷贝、本地写盘及外部副本 |

先预热约 10 个 step，再对后续约 30 个稳定 step 比较；各方案使用相同样本、批量预算和计时方法。CUDA 是异步执行，普通 Python forward 前后计时可能只测到 kernel 提交时间；GPU 阶段应使用 CUDA events。不要每个小算子都 synchronize，这会破坏正常流水线。profiling 版本的开销不能混入正式吞吐声明。

完整时间预算可按下式记录：

```text
总时间 ≈ 模型准备 + 输入缓存准备
       + epochs × 纯训练轮耗时
       + 验证次数 × 完整验证耗时
       + 保存次数 × 检查点耗时
       + 最终测试耗时
```

若“每轮耗时”已经包括验证和保存，不要在公式里重复相加。先用一次完整 epoch、一次完整验证验证外推，再估算 50 轮和剩余种子的日程。

## 5. 第一优先级：缓存输入，保留训练计算

修改位置：T4 的 `LandslideDataset.__getitem__` 与 `read_landslide_sample`。

建议缓存内容是**波段选择和 resize 后、模型归一化前**的 float32 影像及整数标签。保持当前 bilinear / nearest 插值设置、波段顺序、ignore 规则和训练集归一化完全一致。不要为节省空间先改成 FP16；那属于额外数值变更，应另做对照。

以 2400 张、6×224×224、float32 计算，纯影像约 2.89GB（2.69GiB），标签、验证集、缓存索引和进程内存另算。可用 RAM 或本地 NVMe 的只读 mmap 缓存；多进程或 spawn 环境下注意不要给每个 worker 复制一份完整数组。

缓存身份至少包含 manifest 内容哈希、原始文件身份、波段顺序、resize 尺寸/插值、读取实现版本。先对抽样影像和标签逐值核对；现有读取是确定性的，输入缓存应能做到一致。缓存命中不代表可以复用不同数据清单或不同预处理版本。

分别记录首次建缓存与缓存命中的耗时。比较热缓存时，基线也应预热文件系统缓存；不要把一边冷启动、另一边热缓存的差值全算成实现收益。一次性缓存准备成本单独列入总预算。

配套可试：训练 DataLoader 设置 `persistent_workers=(num_workers > 0)`、`pin_memory=True`，GPU 搬运设置 `non_blocking=True`。参数需要同时配合并测量，增加 worker 或 pinned memory 不保证必然提速。若 GPU 计算已占满，这一步可能只节省很小比例。

## 6. 第二优先级：优化验证循环

修改位置：T4 的 `_evaluate`。

先只移除每样本的 `torch.cuda.empty_cache()`，保留 FP32，与原验证实现比较耗时、峰值显存和指标。PyTorch 的缓存分配器会复用已释放显存，逐样本清缓存值得单独对照；没有测量前不宣称能节省多少时间。

随后单独尝试验证 BF16 autocast。该修改只需包住模型前向，混淆矩阵仍用整数计数。不能把“指标看起来差不多”当成完全等价：低精度可能改变 argmax 或最佳 epoch。对同一权重、完整验证集比较 mIoU、前景 IoU、预测分歧以及接近的候选 checkpoint；有差异时可保留 FP32 最终复核并明确选模规则。

本版没有验证 batch 的环境开关。若想增加验证 batch，需修改 DataLoader 并验证显存，不要只设置一个未被读取的变量。

## 7. 第三优先级：注意力实现与硬件安排

本版 `build_backbone` 使用 `AnySat(..., flash_attn=False)`。检查目标环境是否已有兼容的 flash-attn/CUDA/PyTorch；在独立环境或试验版本中打开，再验证前向、loss、adapter 梯度和速度，不在正在跑正式任务的环境里直接升级依赖。

大 micro-batch 不等于更快：先在 4090 上测试 1×2 与 2×1；若原 effective batch=2，不要直接改成 4×1。算子实现、精度和批量布局可能改变随机数消费及浮点误差，同 seed 不保证逐位复现。

安排上，优先让 seed 17 按原计划完成；待 4090 空闲后，用测得的吞吐决定是否在那里启动 42/73。把种子分配到两张卡是缩短日历时间，各自仍是独立单卡实验；不需要把它们改为 DDP。不能仅凭 GPU 型号保证两个种子能在某个固定时限完成。

## 8. 大幅减少重复骨干计算：T4 B2S，另开实验

可以参考 `workers/anysat/src/anysat_worker/t5.py` 的两阶段路径：

1. stage A 在线训练 adapter＋head，骨干冻结。
2. 在预先约定的训练轮数冻结 adapter，保存冻结点。
3. 对训练和验证样本提取一次固定特征，stage B 只训练 head。
4. 用相同的冻结 adapter＋骨干处理最终测试输入，并保留验证选模规则。

T4 当前没有这条路径。不能只在开始时缓存特征然后继续更新 adapter：缓存会立即过期。不同 seed 学到的 adapter 也不能默认共享同一份特征缓存。

按本版 dense 特征为 1536×224×224、FP16 估算，2400 张训练样本的缓存约 **370GB（344.5GiB）**，还没算验证/测试、索引和临时文件。应先实际打印 feature shape/dtype，再决定缓存格式和磁盘预算。每轮读取大缓存及训练空间头仍有成本，不能承诺冻结后就只需几分钟。

缓存指纹至少记录冻结 adapter 权重哈希、骨干权重、manifest、波段/归一化、输入尺寸、patch 参数、特征精度、冻结轮数和代码版本。特征提取应隔离 RNG 消费，避免仅因建缓存改变后续 shuffle/dropout 流。

该方案属于 **B2S**，不能与原 B2 的三个种子合并成 n=3；在 epoch 18 改成冻结 adapter 继续训练，也属于新方案。若主要目标是把当前 B2 矩阵补齐，优先考虑工程优化和调度，而不是临时改协议。

## 9. 验收表和恢复注意事项

每次只改变一项，先确认结果正确，再比较速度。下面表格可直接填写：

| case / commit / GPU | micro×accum | 输入/精度/注意力 | 数据等待 | 稳定训练 ms/图 | 完整验证 s | checkpoint s | 峰值 MB | 输出与梯度检查 |
|---|---|---|---:|---:|---:|---:|---:|---|
| baseline | 1×2 | 原实现 | | | | | | |
| 输入缓存 | 同 baseline | FP32 输入缓存 | | | | | | |
| 验证不清缓存 | 同 baseline | FP32 验证 | | | | | | |
| BF16 验证 | 同 baseline | BF16 验证 | | | | | | |
| 注意力加速 | 同 baseline | 记录具体版本 | | | | | | |
| 4090 batch 对照 | 2×1 | 其余同 baseline | | | | | | |

正式放行前至少检查：

- 样本清单、划分、六波段顺序、224 输入、损失、标签支持集和有效 batch 没被顺带改变。
- 短跑 loss 有限，adapter 的参数确实更新；没有通过 `no_grad` 误切断 adapter 梯度来“提速”。
- 完整验证集和验证频率符合原协议，模型选择只用验证集，最终测试不用于选择提速方案。
- 测速记录在独立根目录，不复制为正式结果；正式运行清除短跑 epoch/batch/eval 限制。

测速配置使用了 `ANYSAT_WORKER_EPOCHS=2`、`ANYSAT_WORKER_LIMIT_BATCHES=50` 和 `ANYSAT_WORKER_EVAL_LIMIT=16`。**不要直接在这个 shell 里启动正式任务。** 最简单的做法是另开 shell，重新加载正式配置，确认 50 epochs、无 train/eval 截断以及正确账本路径后再运行。

当前续训会比较代码版本、权重/manifest/config 哈希、PyTorch 版本、CPU/CUDA 设备类型以及 epochs、micro-batch、累积、lr、验证频率等设置。改代码或 batch 后，旧 `latest.pt` 可能被拒绝恢复；smoke 检查点也不能直接续成 50 轮正式实验。不要修改检查点身份绕过检查。跨 GPU 即使通过兼容性检查，也不保证逐位相同。详见[断点续训说明](断点续训与Colab运行.md)。

## 10. 第一轮建议怎么选

1. 保留 seed 17 原任务，在另一空闲时段/卡上完成短跑基线。
2. 先测 worker 数、输入缓存、验证阶段去除逐样本清缓存；再测数值路径变化。
3. 记录一次完整 epoch 和完整验证，得到真实剩余时长，再决定 42/73 是否挪到 4090。
4. 若 T4 只是辅助能力、资源仍不足，完整完成 seed 17 并标注 n=1，比把不同预算或不同冻结方案拼成 n=3 更容易解释。
5. 需要长期多次跑 AnySat T4 时，再投入 T4 B2S 和特征缓存实现。

减到 128 输入、加大 patch、减少 epoch、减少训练样本或降低验证频率都会改变实验条件，不能作为保持原协议的纯工程加速。

参考：[PyTorch AMP](https://docs.pytorch.org/docs/stable/notes/amp_examples.html)、[CUDA 缓存分配器](https://docs.pytorch.org/docs/stable/notes/cuda.html#cuda-memory-management)、[AnySat 官方说明](https://github.com/gastruc/AnySat)、本项目 `t4.py` / `t5.py` / `checkpoint.py`。
